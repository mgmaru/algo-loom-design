# ADR-0013 `V-12E`の受け渡しは原因を特定してから直し、helperの成功報告を到達と切り離す

| 項目 | 内容 |
|---|---|

## 背景と前提

2026年9月21日、5回目のcampaign `v12-2026-09-21-01`で`V-12A`・`V-12B`・`V-12C`の必須case・`V-12D`が合格し、`V-12E`へ進みました。再認証が成立し、提出確認画面まで到達し、**「AtCoderの提出画面へ進む」のPOSTもhelperが受理しました。** 4回目の`authentication_rejected`（[ADR-0012](0012-serve-submission-page-with-same-origin-referrer-policy.md)）は再発していません。

止まったのはその次です。**browserはAtCoderの提出pageへ着かず、`http://127.0.0.1:<待受番号>/submission/proceed`で`ERR_CONNECTION_REFUSED`を表示しました**（[実行記録 §8](../verification/judge-adapter/results/2026-09-21-v12-04.md#8-v-12eが最後の受け渡しに到達しなかった理由)）。

判断の土台にした事実です。

| # | 前提 | 根拠 |
|---|---|---|
| 1 | browserは提出pageのURLではなく、**loopbackの`/submission/proceed`でエラーを表示した。** runtime profileの履歴にも提出pageの訪問記録がない | 2026年9月21日の人の観測と、使い捨てruntime profileの履歴 |
| 2 | helper側ではPOSTが受理され、`serveSubmission`が303を書き、押下の通知を受けた本体が`server.Shutdown`へ入っている | helperの結果JSON（`confirmation_shown: true`、`submit_page_redirect_issued: true`）と待受の停止 |
| 3 | `ERR_CONNECTION_REFUSED`は、browserが**その待受番号へあらためて接続して拒否された**ことを示す。送ったPOSTの応答を受け取れないまま接続が終わり、接続し直したときには待受が閉じていた | Chromeのエラー分類 |
| 4 | **最初に立てた仮説は実測で否定された。** 「303を書く前に押下を通知するため、`Shutdown`が応答の書き込みに先回りする」という説明は、Goの`http.Server.Shutdown`が処理中のrequestを待つため成立しない | 2026年9月21日にhelperと同じ順序をリポジトリ外で再現し、4条件×20回で測った。**すべての条件で303が届いた**（[実行記録 §8.2](../verification/judge-adapter/results/2026-09-21-v12-04.md#82-実測で否定した仮説)） |
| 5 | helperが観測できるのは303を書いたところまでで、**browserが提出pageへ着いたことは観測できない。** 到達は人の観測として記録する取り決めである | [検証物README](../../scripts/verification/atcoder_v12/README.md)、[ADR-0011](0011-add-submit-entry-before-rerunning-v12.md) |
| 6 | そのため、helperは到達していないのに`ok: true`を返した。**結果JSONだけを見た人は`V-12E`が成立したと読む** | 5回目の結果JSON |
| 7 | helperのbuild hashが変われば`V-12A`〜`V-12E`のすべてが無効になり、新しいcampaignが必要になる | [ADR-0007](0007-make-helper-build-hash-track-behaviour.md)、検証計画の無効化表 |
| 8 | 人の操作が要るのは`V-12B → V-12D`と`V-12E`で、1回あたり15分程度かかる。5回目までに4回やり直している | 2026年9月19日から21日のcampaign記録 |
| 9 | 拡張機能のsourceを変えると、Chrome Web Storeへの再提出と審査が発生する | [ADR-0012](0012-serve-submission-page-with-same-origin-referrer-policy.md)前提7 |

## 決定

1. **原因を特定するまで、この受け渡しを直しません**（[`TD-53`](../../TODO.md#td-53-提出確認画面から提出pageへの受け渡しが成立しない原因を特定する)）。前提4のとおり、最初の仮説はすでに実測で否定されています。**症状に合う説明が立つまで、コードへ触れません**
2. **特定は、browserが応答を受け取り遷移し終えるところまでを測るprobeで行います。** ローカルだけで完結させ、AtCoderにもChrome Web Storeにも接続しません。**negative controlを必ず含め、「受け渡しが壊れている条件を検出できる」ことを先に示します**（[ADR-0012](0012-serve-submission-page-with-same-origin-referrer-policy.md)決定3と同じ規則）
3. **helperの結果JSONを、到達していないことが読み取れる形にします**（[`TD-54`](../../TODO.md#td-54-helperの成功報告が到達していないことを覆い隠さないようにする)）。`ok: true`の意味を「helperが観測できた範囲が成立した」に限定し、**`V-12E`の合否をhelper単独で述べません**
4. **`TD-53`と`TD-54`は同じ変更にまとめます。** 前提7・8により、個別に直すとそのたびにcampaignが無効になり、人の15分がもう一度必要になります（[ADR-0011](0011-add-submit-entry-before-rerunning-v12.md)決定3と同じ理由）
5. **campaign `v12-2026-09-21-01`は、この修正をもって無効になります。** 6回目で`V-12A`からやり直します。5回目の記録は消さずに残します

## 検討して採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| 通知と応答の順序を入れ替え、6回目のcampaignで確かめる | **前提4で否定済みの修正である。** 直っていないものを直したと記録し、人の15分を使う6回目で同じ場所に止まる。「たぶんこれだろう」を実機で試す場所が、最も高くつく場所になっている |
| `Shutdown`を固定時間（例: 5秒）遅らせる | 症状は消えるかもしれないが、**直ったのか、たまたま間に合っただけなのかを区別できない。** 原因を特定したうえでの手段としては残しうるが、特定の代わりにはならない |
| 提出確認画面にJavaScriptを入れ、`location.assign`で遷移する | [ADR-0011](0011-add-submit-entry-before-rerunning-v12.md)が画面をJavaScriptなしに設計した理由が残っている。加えて**原因が分からないまま形を変えると、何が効いたのかが分からない。** 直ったように見えても、同じ原因が別の場所に残る |
| `V-12E`の合格条件から到達を外し、303の発行をもって合格とする | **確かめたい性質そのものを捨てる。** `V-12E`は「同じbrowserで、一往復で提出画面まで進めるか」を見ている。[ADR-0011](0011-add-submit-entry-before-rerunning-v12.md)が却下した「人が手で提出pageを開いて合格とする」と同じ帰結になる |
| helperの`ok: true`をそのままにし、記録の書き方で補う | [`TD-50`](../../TODO.md#td-50-helperの誤った成功報告と原因を指せないエラー名を直す)で直したのと同じ型の報告を残すことになる。**人が毎回正しく読み替える前提の記録は、いつか読み替えられない** |
| 6回目のcampaignを先に回し、再現するかを見る | **人の15分を原因調査の手段として使うことになる。** ローカルで測れる範囲を実機で測る理由がない。前提8のとおり、やり直しはすでに4回になっている |

## 理由

2つあります。

第一に、**実測で否定された仮説は、この経路について自分たちのモデルが症状を説明できていないことを示しています。** 説明できないまま直すと、直ったことも直っていないことも確かめられません。[ADR-0005](0005-verify-consent-flow-in-browser-semantics.md)と[ADR-0012](0012-serve-submission-page-with-same-origin-referrer-policy.md)は、どちらも**browserで何が起きるかを測らずに決めた**ために実機で止まりました。今回は同じ型を、コードへ触れる前の仮説の段階で止めています。前提4の測定に15分もかかっていません。**測る前に直していたら、人の15分を使うcampaignで気づくことになりました。**

第二に、**到達の観測が人の目にしか残らない構造は、報告と結果のずれに誰も気づけません。** 前提5と6のとおり、helperは自分が観測できない範囲を`ok: true`で覆っています。今回は人がエラー画面を見ていたため気づけましたが、**見ていなければ「`V-12E`合格」として記録されていました。** これは`TD-50`で直した「消したつもりで残る」と同じ型です。

## 影響と再評価条件

- **5回目のcampaignの`V-12A`・`V-12B`・`V-12C`・`V-12D`の合格は、修正をもって取り消されます。** 記録は[`v12-04`](../verification/judge-adapter/results/2026-09-21-v12-04.md)に残します
- **人の操作が要る`V-12B → V-12D`を、もう一度15分やり直すことになります。** これで4回目です
- **Chrome Web Storeの再審査は発生しません。** 前提9のとおり、拡張機能のsourceを変えないためです
- **`V-12E`は不合格ではありません。** 再認証と提出確認画面、POSTの受理までは成立しており、確かめられていないのは最後の受け渡しだけです。方式Aの成立性そのものへの否定的な証拠ではありません
- **原因が判明した場合、その契約は製品実装にも当てはまりえます。** loopback画面からform POSTで遷移する形は製品でも採りうるため、観測した事実は[`TD-38`](../../TODO.md#td-38-認証配布物とテンプレートのライフサイクル契約を確定する)へ渡します

次のいずれかが起きたら見直します。

- **probeでも原因を特定できず、ローカルで再現できないとき。** 実機のcampaignで観測を取る設計へ切り替えます。その場合は**何をどこに記録するかを先に決めます。** 人の操作を使う以上、同じ実行から最大限の観測を取る必要があるためです
- **原因が「loopback画面からのform POSTで別originへ303する」という形そのものに内在すると分かったとき。** 受け渡しの設計を見直し、[ADR-0011](0011-add-submit-entry-before-rerunning-v12.md)決定2を再評価します
- **helperが観測できない範囲が他にもあると分かったとき。** 実行して評価する範囲の定義（[ADR-0008](0008-scope-of-execution-based-checks-for-verification-artifacts.md)）から見直します
