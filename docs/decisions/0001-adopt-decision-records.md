# ADR-0001 決定記録を導入し、判断の時点記録を残す

| 項目 | 内容 |
|---|---|
| 状態 | 採用 |
| 日付 | 2026年9月18日 |
| 関連TODO | ―（TODOに属さない判断） |
| 正本 | [決定記録の書き方](README.md) |

## 背景と前提

このリポジトリは設計判断の正本を`docs/`に置き、判断の理由も各文書へ書いてきました。第三者が設計理由を読める状態は、おおむね達成できています。

一方で、**判断が覆ったとき、覆る前の理由がその場から消えます。** `docs/`の各文書はトピック別に現在の状態を書くもので、更新は上書きだからです。残るのはgit履歴の中だけで、実質追えません。

2026年9月18日時点の実測です。

| 観測 | 値 |
|---|---|
| 覆った判断・訂正を記録している文書 | 8ファイル |
| うち5件が集中している文書 | [CWS配布準備](../verification/judge-adapter/v12-chrome-web-store-preparation.md) |
| その他の文書での記録 | 1〜2件 |

`TD-39`で「停止理由として記録した4項目のうち2項目は誤った前提に基づいていた」と残せたのは、そこがたまたま検証記録という不変寄りの文書だったためです。仕組みではなく偶然でした。

判断の土台にした前提は次の3つです。

1. **トピック別の文書は上書き更新されるため、覆った理由を保持できない。** 上の実測がこれを示す
2. **決定の多くはこれから発生する。** 工程4は進行中で、工程6の実装は未着手である。遡及しなくても実用になる
3. **TODOと決定は N 対 N である。** `TD-39`単独で6つの判断（reviewer用helperの受渡し方式、Apple Developer Programへ加入しない、審査と公開の分離、最終campaign manifestの生成を`TD-11`へ置く、`V-12A`での配信bytes取り直し、標準追加の確認にシークレットモードを使わない）が生じた。一方で方式Aの製品形態は`TD-09`と`TD-10`の双方から出ている

## 決定

決定記録（ADR）を[`docs/decisions/`](README.md)へ導入します。あわせて次を決めます。

1. **ADRは判断した時点の記録とし、本文を書き換えません。** 判断が変わったら新しいADRを書き、旧ADRには状態と行き先のリンクだけを追記します
2. **`docs/`を現在の仕様の正本として維持します。** ADRは現在の仕様を再掲せず、正本へのリンクを持ちます
3. **過去の決定へ遡及しません。** 2026年9月18日以降の判断から適用します
4. **ADRの番号をTODOのIDと一致させません。** 独立した連番とし、対応付けは相互リンクで表現します
5. **TODO.mdの一覧表へ「決定」列を追加します。** どのTODOがどの決定を生んだかを一覧で見られるようにします
6. **相互リンクの整合を`node scripts/check-docs.mjs`で検査します**

## 検討して採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| ADRを導入しない | `TODO.md`の肥大はADR不在が原因ではなく（1856行のうち判断記録は10件）、その点では不要だった。しかし**覆った理由が残らない**という欠落は別に実在し、これを埋める手段が他にない |
| ADRの番号をTODOのIDと一致させる | 前提3のとおり N 対 N であり、1対1に割り当てられない。加えてTODOのIDは追加順で意味を持たず、`TODO.md`の対象は工程4と工程5に限られる。**消える側の採番へ、残る側を従属させることになる。** 相互リンクなら片側だけの記載を機械的に検出できるが、番号一致では破綻に気づけない |
| 過去の決定へ遡及する | 費用が効果に見合わない。必要になった決定だけ、そのとき書けばよい |
| `docs/`の各文書へ判断履歴の節を設ける | 上書き更新される文書の中に不変の記録を置くことになり、同じ問題が再発する |

## 理由

3つあります。

第一に、**覆った理由が残らないという欠落を、他の手段で埋められません。** git履歴は残りますが、「どの前提が誤っていたか」を辿る読み物にはなりません。

第二に、**不変の時点記録と可変の正本は、役割が違うため両立します。** 当初は「`docs/`と`spec/`に加えてADRを持つと三面整合になる」ことを懸念しましたが、ADRが現在の仕様を再掲しなければ整合の対象になりません。ADRは古くなっても誤りにならず、置き換えられるだけです。

第三に、**前提を明示する欄を持つことが、後からの評価を可能にします。** 判断が誤っていたかどうかは、前提と実際に起きたことを突き合わせて判定します。前提が書かれていなければ、結果の良し悪ししか言えません。

## 影響と再評価条件

影響は次のとおりです。

- 判断を行ったら、その変更と同じ単位でADRを書きます（[作業ガイド](../../CLAUDE.md)へ規約を追記）
- `TODO.md`の一覧表が6列になります。`scripts/todo-status.mjs`を同じ変更で対応させました
- 当面、多くのTODOの「決定」列は`―`です。遡及しないため、埋まるのは今後の判断からです

次のいずれかが起きたら見直します。

- **遡及しないことで支障が出たとき。** 過去の決定の理由を辿れず判断が止まる場面が実際に生じたら、その決定だけADRへ起こします
- **一覧が機能しなくなったとき。** ADRが増えて一覧表から目的の決定を見つけられなくなったら、分類または索引を追加します
- **`TODO.md`が役目を終えるとき。** 工程6以降、TODOによる追跡が終わったら「決定」列の扱いを見直します。ADRはそのあとも残ります
