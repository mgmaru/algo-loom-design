## 背景と前提

[`TD-12`](../../TODO.md#td-12-3つのosの認証検証マトリクスを作る)は[`TD-11`](../../TODO.md#td-11-方式a製品形態を実サービスで検証する)に依存します。`TD-11`（`V-12`の3回目のcampaign）は未実施で、実行には人の明示承認とAtCoderへの接続が要ります。**依存が解けるまで何も進めないか、依存しない範囲を先に進めるかを決める必要がありました。**

判断の土台にした事実です。

| # | 前提 | 根拠 |
|---|---|---|
| 1 | `TD-11`の実行にはAtCoderへの接続を伴うため、人の明示承認が要る | [作業ガイド §4](../../CLAUDE.md#4-外部操作には明示承認が必要) |
| 2 | 2回目のcampaignで`V-12A`・`V-12B`・`V-12D`が実機で合格した。無効にした理由はhelperのbuild hash変更であり、**不具合が見つかったのではない** | [ADR-0007](0007-make-helper-build-hash-track-behaviour.md)、[実行記録](../verification/judge-adapter/results/2026-09-20-v12-01.md) |
| 3 | `V-12`の合格が示すのは代表環境までで、3つのOSへの横展開は`TD-12`が独立に扱う | [ADR-0009](0009-required-cases-for-v12c.md) |

## 決定

1. **`TD-12`のうち`V-12`の結果に依存しない範囲を先に作り、[認証設計 §6.2](../architecture/atcoder-authentication.md#62-3つのosの認証検証マトリクス)へ暫定として置きます。** 依存する部分は`M-05`〜`M-08`、`M-13`、`M-14`として名指しし、§6.2.8に未確定として列挙します
2. **行を環境IDで定義し、確認層が同じ環境は3つのOSの列へまとめます。** 環境ごとの差は上書き表（§6.2.4）だけで持ちます
3. **macOSの秘密情報保管庫は実観測し、[§4.1.1](../architecture/atcoder-authentication.md#411-macosで観測した実際の保証範囲)へ記録します。表示文言は確定しません。** 3つのOSが揃うまで未決事項 7.3 を未決のまま保持します
4. **残りを[`TD-46`](../../TODO.md#td-46-検証マトリクスを確定しwindowsとlinuxの秘密情報保管庫を観測する)として起票し、`TD-12`は進行中のままにします。** 完了条件を満たさないものを完了にしません

## 検討して採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| `TD-11`の完了を待ってから`TD-12`へ着手する | 前提1により`TD-11`の開始時期を`TD-12`の側から決められない。前提3で`TD-12`はもともと独立に進める設計であり、完了条件のうち手動受け入れ操作の区別、VM・物理端末・実サービスの分担、秘密情報保管庫の観測は`V-12`の結果に依存しない。**待っても内容が変わらない作業まで止まる** |
| `V-12`の合格を仮定してマトリクスを確定する | 前提8と矛盾する。加えて前提6により、秘密情報保管庫の表示文言を実観測なしに確定すると、利用者へ示す約束を観測なしで決めることになる |
| 7つの環境 × 21項目を全て展開する | 147セルのうち環境で差が出るのは10セル程度で、残りは同じ内容の写しになる。**写しは片側だけ直したときに食い違う。** `check-docs.mjs`が検出できるのはリンクの食い違いだけで、表の内容の食い違いは検出できない |
| マトリクスを新しい文書として作る | `TD-12`の対象ファイルは認証設計 §6であり、確認層の定義は§6.1にある。**層の定義と層の割り当てを別文書へ分けると、層を増減したときに片方だけが残る** |
| macOSの観測も`TD-46`へ回す | 前提5のとおり今すぐ観測でき、観測しなければ分からない事実があった（次節） |

## 理由

2つあります。

第一に、**依存しているのは「結果」であって「作業」ではありません。** `TD-12`が`TD-11`に依存するのは、確認項目の一覧が`V-12`の結果で変わるためです。確認層の割り当て方、手動で受け入れる操作の境界、VMと物理端末の分担は、`V-12`の前後で変わりません。変わる部分を名指しできる以上、暫定と確定を分けられます。

第二に、**観測できるものを先に観測すると、理由からは導けない事実が出ます。** §4.1は「信頼される実行ファイルはインタプリタになる」を理由から導いていました。観測するとそのとおりでしたが、加えて**アクセス制御の信頼実行ファイル一覧が汎用インタプリタを締め出さない**ことが分かりました。ad-hoc署名の実行ファイルが作成し、読み出し許可にその実行ファイル1件だけを持つ項目を、Apple署名のPythonが確認画面なしで読み出せています。これは理由からは導けておらず、先に観測しなければMVPの直前まで分からないままでした。

## 影響と再評価条件

- **§6.2は暫定です。** `V-12`が不合格なら`M-05`〜`M-08`、`M-13`、`M-14`を作り直します
- **未決事項 7.3 は未決のままです。** macOSだけの観測で表示文言を確定しません
- **`TD-12`は進行中です。** 実装開始条件の充足判断（`TD-28`）は`TD-12`の完了を待ちます
- macOSのアクセス制御が汎用インタプリタを締め出さないという観測は、**仕組みを特定していません。** 事実としてだけ記録し、配布形態が決まった時点で再確認します

次のいずれかが起きたら見直します。

- **`V-12`が不合格で方式Aを再設計するとき。** §6.2の確認項目を作り直します
- **WindowsまたはLinuxの観測で、macOSと異なる保証範囲が出たとき。** 3つのOSで共通の表示文言にできるかを決め直します
- **`TD-31`がCPU architectureと対応Chromeの版を固定したとき。** §6.2.1の行と§6.2.7の変更提案を見直します
- **macOSのアクセス制御の仕組みが特定できたとき。** §4.1.1の観測記述を仕組みの説明へ置き換えるかを判断します
