## 背景と前提

[検証計画](../project/judge-adapter-verification.md#311-v-12-方式a製品形態の検証)は2箇所で「`V-12C`の必須case」と書いていますが、**どれが必須かの一覧がありませんでした。** `V-12E`の事前条件と`V-12C`の合格条件がこの語を使うため、決めないと**どこまでやれば`V-12E`へ進んでよいかを実行中に判断することになります。**

判断の土台にした事実です。

| # | 前提 | 根拠 |
|---|---|---|
| 1 | `V-12C`の検証層は3つある。OS非依存の契約test、3 OS統合test、更新導線だけの配布導線test | [検証計画の`V-12C`](../project/judge-adapter-verification.md#311-v-12-方式a製品形態の検証) |
| 2 | `V-12E`が使うのは、基準template、確認済みlocal sessionの削除、別のCLI実行からの再認証、同じbrowserでの提出確認画面までである。**更新導線は経路に現れない** | 同 `V-12E`の定義 |
| 3 | 無効化表は「OS・CPU architecture・secret store実装 → **該当環境の**`V-12C`・`V-12E`」と、結果を環境ごとに切り分けている | 同 無効化表 |
| 4 | 無効化表は「更新test用の版の組だけ → `V-12A`の版照合case、`V-12C`の**更新case**」と、更新導線を独立caseとして切り出している | 同 |
| 5 | 3 OSの検証マトリクスは[`TD-12`](../../TODO.md#td-12-3つのosの認証検証マトリクスを作る)が扱い、`TD-11`の後続として立っている | [TODO.md](../../TODO.md) |
| 6 | 更新test用の版のuploadと審査提出には、別の明示承認が要る | [作業ガイド §4](../../CLAUDE.md#4-外部操作には明示承認が必要) |
| 7 | native LinuxとWindowsの実機を現在持っていない | 2026年9月20日時点 |

## 決定

1. **`V-12C`の必須caseを、代表環境で実行する5つの契約testに定めます。** 中断の各境界での安全側停止、対象版・権限・配布元の不一致、基準templateの破損、secret store障害、process・待受・file lockの競合です。一覧は[検証計画](../project/judge-adapter-verification.md#311-v-12-方式a製品形態の検証)を正本とします
2. **Chromeの更新、拡張機能の更新、3 OS統合testは必須caseに含めません。** 前提2により`V-12E`の経路に現れず、前提3と4により独立caseとして後から足せます
3. **`V-12`の合格が何を示さないかを、検証計画へ明記します。** 「代表環境で方式Aの一往復UXが成立する」までであり、3つのOSでの成立と更新導線の成立は示しません
4. 3 OSは[`TD-12`](../../TODO.md#td-12-3つのosの認証検証マトリクスを作る)、更新導線は`V-12C`へ後から足すcaseとして残します。**外したのであって、やらなくてよくなったのではありません**

## 検討して採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| 必須case＝`V-12C`の全case（3 OSと更新導線を含む） | native LinuxとWindowsの実機（前提7）と、更新版のupload・審査（前提6）が揃うまで**`V-12`が判定不能のまま止まる。** `V-12`の目的は方式Aという製品形態が成立するかの判断であり、**1つの環境で成立しなければ3 OSでも成立しない。** 横展開を待つ理由がない |
| 更新導線だけ必須に含める | `0.1.2`のuploadと審査で数日から数週間かかる。前提2のとおり`V-12E`の経路に現れないため、`V-12E`を待たせる根拠がない |
| 必須caseを決めず、実行しながら判断する | **判断基準が曖昧なまま進めると、後から「これでは足りなかった」と分かる形になる。** `V-12C`の合格条件そのものが「必須caseが合格し」と書かれているため、決めないと合否を言えない |
| `V-12`の合格条件から「必須case」という語を消し、全caseを要求する | 1案目と同じ帰結になる。加えて、環境ごと・case ごとに結果を切り分ける無効化表（前提3、4）と矛盾する |

## 理由

2つあります。

第一に、**`V-12E`が実際に依存するもので線を引けます。** `V-12E`は基準templateと削除契約と再認証導線を使います。必須にした5つはすべてその経路に現れ、外した3つは現れません。「念のため全部」ではなく、依存関係で決めました。

第二に、**`V-12`の目的は横展開ではなく成立性の判断です。** 代表環境で成立しなければ方式Aを設計し直すことになり、3 OSの結果は使いません。逆に成立すれば、横展開は`TD-12`が独立に進められます。**成立性の判断を横展開の準備で待たせる構造になっていました。**

## 影響と再評価条件

- **`V-12`合格の主張が限定されます。** 代表環境（macOS arm64）までです。この限定を検証計画へ明記したため、後から「3 OSは未確認だった」と気づく形にはなりません
- `TD-12`は`V-12`合格後も残ります。**MVPの実装開始条件を判断するときは、`V-12`合格だけを根拠にしません**
- 更新導線のcaseを後から足すとき、無効化表により影響するのは`V-12A`の版照合caseと`V-12C`の更新caseだけです。**実サービスsmokeの再実行は発生しません**

次のいずれかが起きたら見直します。

- **代表環境の必須caseで、他環境にも同じ影響が出ると分かる不具合が見つかったとき。** 3 OSを`V-12`の前提へ戻すかを判断します
- **更新導線の不成立が、初回導線の成立を否定しうると分かったとき。** 前提2が崩れるため、更新caseを必須へ移します
- **代表環境を変えるとき。** 無効化表により`V-12B`・`V-12D`を含めて取り直しになります
