# ADR-0002 CIで検査を自動化し、`main`をPR経由に限定する

| 日付 | 2026年9月18日 |
| 関連TODO | ―（TODOに属さない判断） |

## 背景と前提

[作業ガイド](../../CLAUDE.md)は変更のたびに4つの検査を実行すると定めていますが、実行は人の記憶に依存していました。2026年9月18日にPRを使い始めたため、機械で回す前提が整いました。

同日、`TD-39`の完了条件を確認する過程で、CLI例へ端末の利用者名と同じ値（`--user`の引数）が書かれているのを**手作業で**見つけました。規約違反を検出する仕組みがなく、人が気づくかどうかに依存していたことになります。

判断の土台にした事実は次の4つです。いずれも同日の実測または公式資料です。

| # | 前提 | 根拠 |
|---|---|---|
| 1 | CIはubuntuで動く | macOS固有のcaseは`process.platform !== "darwin"`と`runtime.GOOS != "darwin"`でskipされる。実測でガードを確認した |
| 2 | ただしmacOS固有の観測はCIでは検証されない | skipされるのは、quarantine属性の伝播とad-hoc署名の実行可否。`TD-39`で最も重要だった観測である |
| 3 | 費用は発生しない | 「GitHub Actions usage is free for self-hosted runners and for public repositories that use standard GitHub-hosted runners」。larger runnerは公開リポジトリでも課金対象 |
| 4 | **PRの作成者は自分のPRを承認できない** | GitHubの仕様。一人で開発する現状では、承認を必須にすると全PRがmergeできなくなる |

## 決定

1. **GitHub Actionsで検査を回します。** `main`へのPRと`main`へのpushを契機とします
2. **検査を5つにします。** 既存の4つに加え、[`scripts/check-forbidden.mjs`](../../scripts/check-forbidden.mjs)で禁止事項を走査します
3. **CIから外部サービスへ接続しません。** 接続を伴う検証は人の明示承認が要り（[作業ガイド §4](../../CLAUDE.md)）、CIは承認を得られる実行主体ではないためです
4. **`main`への直pushを禁止し、すべての変更をPR経由にします。** ブランチは短命とし、`docs/`、`chore/`、`fix/`、`feat/`を接頭辞にします
5. **Approveを必須にしません。** 代わりに、`docs/decisions/`を変更するPRでは[確認項目](../../.github/pull_request_template.md)が埋まるまでCIが通らないようにします
6. **管理者のbypassを当面許可します**

## 検討して採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| Approveを必須にする | 前提4のとおり、一人では物理的にmergeできなくなる。管理者bypassで回避すれば、設定した意味がなくなる |
| git-flowのような多段のブランチ戦略 | このリポジトリにreleaseもversionもない。設計文書の変更に`develop`と`release`を挟む理由がない |
| 軽微な変更は直pushを許す | 「軽微かどうか」を毎回判断する費用が生じ、誤爆のリスクが残る。CWS listingが参照する2ファイルのように、**軽微に見えて外部へ即座に露出する**変更が実在する |
| macOS runnerも常時回す | 前提2のskip対象は環境の観測であり、回帰検出の対象ではない。観測結果は[CWS配布準備](../verification/judge-adapter/v12-chrome-web-store-preparation.md)へ記録済みである。必要になった時点で足す |
| 禁止事項の走査を実名の一覧で行う | **検知パターンへ実名を書けば、そのパターン自体が規約違反になる。** 形式で判別できるものに限る |

## 理由

3つあります。

第一に、**検査が人の記憶に依存している状態を解消できます。** 5つとも決定論的で、外部接続がなく、実行時間も短いため、自動化の障害がありません。

第二に、**規約違反の検出を仕組みにできます。** 今日の発見は偶然でした。形式で判別できる違反（端末の絶対path、固定ID、秘密鍵、token、Cookieの値、小文字のuser指定）は、以後CIが落とします。

第三に、**承認が使えない制約のもとでも、確認の強制はできます。** Approveの代わりに自己確認の記入を要求すれば、項目を読まずには通せません。形式的だという批判はあり得ますが、何も強制しない状態よりは確実です。

## 影響と再評価条件

影響は次のとおりです。

- `main`へ直接pushできなくなります。緊急時は管理者bypassを使い、使ったことを記録します
- `docs/decisions/`を変更するPRでは、[PRテンプレート](../../.github/pull_request_template.md)の「判断の確認」を埋めないとmergeできません
- **形式で判別できない違反は残ります。** 実名そのものはCIで検出できません。CLI例のplaceholderを大文字に統一する規約で緩和しますが、完全ではありません

次のいずれかが起きたら見直します。

- **開発者が増えたとき。** 前提4が変わるため、Approveを必須にします
- **macOS固有の保証が必要になったとき。** 前提2の範囲を超える回帰を防ぎたくなったら、macOS runnerのjobを足します
- **CIが遅くなったとき。** jobの分割やpath filterを検討します
- **形式で判別できない違反が実際に混入したとき。** 走査の方式を見直します
