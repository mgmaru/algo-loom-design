## 背景と前提

2026年9月20日、3回目のcampaign `v12-2026-09-20-02`で`V-12A`・`V-12B`・`V-12C`の必須case・`V-12D`が合格しました。続けて`V-12E`へ進もうとして、**検証物に`submit`相当の入口が無いことが分かりました。**

`V-12E`が要求するのは次の一連です。

| # | 要求 | 出典 |
|---|---|---|
| 1 | `submit`相当の入口が、再認証の理由と中止方法を表示する | [検証計画の`V-12E`](../project/judge-adapter-verification.md#311-v-12-方式a製品形態の検証) |
| 2 | 同じ入口がbrowserを自動起動する | 同 |
| 3 | 利用者の認証固有操作をAtCoder loginだけにする | 同 |
| 4 | 認証後、**同じbrowser**で対象・言語・sourceを示す提出確認画面まで進む | 同 |
| 5 | 手動ページ探索とcopy-and-pasteを要求しない。要求したら不合格 | 同（停止条件） |

現在の検証物が持つhelperのcommandは`manifest`、`profile`、`serve`、`first-login`、`recheck`、`secret`、`version`です。判断の土台にした事実です。

| # | 前提 | 根拠 |
|---|---|---|
| 1 | `submit`相当の入口はhelperにもscriptにも存在しない | 2026年9月20日に`atcoder_v12/`を走査。`submit`という語が実装側に1件もない |
| 2 | 拡張機能は認証後に`https://atcoder.jp/settings`へ遷移するだけで、問題の提出ページへは遷移しない | `extension/bootstrap.js` |
| 3 | `serve`は**利用者がChromeを完全終了するまで成功を返さない。** 認証成立の時点を外部へ通知しない | `helper/main.go`、[検証物README](../../scripts/verification/atcoder_v12/README.md) |
| 4 | 対象・言語・sourceを扱う経路が検証物に無い。`V-12E`の入力は「終了済み過去問1件の提出前入力」である | 検証計画の`V-12E`の入力 |
| 5 | helperのbuild hashが変われば`V-12A`〜`V-12E`のすべてが無効になり、新しいcampaignが必要になる | [ADR-0007](0007-make-helper-build-hash-track-behaviour.md)、検証計画の無効化表 |
| 6 | 拡張機能のsourceを変えると、Chrome Web Storeへの再提出と審査が発生する | [ADR-0008](0008-scope-of-execution-based-checks-for-verification-artifacts.md)の前提7 |
| 7 | この不足は`TD-37`から存在していた。`V-12E`へ到達したのが今回が初めてだったため、それまで現れなかった | 1回目は`V-12D`の手前で停止、2回目は`V-12C`の手前で停止 |

## 決定

1. **`V-12E`の`submit`相当の入口を検証物へ足します**（[`TD-49`](../../TODO.md#td-49-v-12eのsubmit相当の入口を検証物へ足す)）。合格条件を緩めず、回避策も足しません
2. **入口はhelper側へ実装し、拡張機能のsourceは変えません。** 前提6により、拡張機能を変えるとCWSの再審査が発生します。前提2の遷移は認証のためのものなので、提出確認画面への遷移は入口側の責務にします
3. **同じ変更で、今日見つけたhelperの2件の欠陥も直します**（[`TD-50`](../../TODO.md#td-50-helperの誤った成功報告と原因を指せないエラー名を直す)）。前提5により、別々に直すとそのたびにcampaignが無効になります
4. **campaign `v12-2026-09-20-02`は、`TD-49`と`TD-50`の修正をもって無効になります。** 4回目のcampaignで`V-12A`からやり直します。3回目の記録は消さずに残します

## 検討して採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| 利用者に提出ページのURLを手で開いてもらい、`V-12E`を合格とする | **停止条件そのものである。** 「手動ページ探索とcopy-and-pasteを要求しない」が合格条件であり、手で開いた時点で不合格になる。確かめたいのは一往復のUXが成立するかであって、画面が表示できるかではない |
| helperを変えず、外側のscriptだけで入口を作る | 前提3により、`serve`は認証成立を外部へ通知せず、Chrome完全終了まで戻らない。**認証成立後・Chrome終了前に提出確認画面を開く手段が外側にない。** secret storeを監視して成立を推測する形は、確かめたい事象の代理をまた一つ増やすことになる（[ADR-0007](0007-make-helper-build-hash-track-behaviour.md)で避けた形） |
| `V-12E`の合格条件から「同じbrowserで提出確認画面まで」を外す | `V-12E`は**方式Aの一往復UXが成立するかを判定する唯一のsub検証**である。外すと`V-12`全体が「認証だけは成立する」ことしか示さなくなる。[AtCoder認証UX設計 §6](../project/atcoder-authentication-manual-operation-automation.md#6-採用条件)の採用条件のうち2件がこの区間に対応している |
| 製品の`aloom submit`を先に実装し、それを入口として使う | 製品実装は`V-12`の合格を待って始める。**順序が逆になる。** 検証物のコードは製品へ流用しない境界も崩れる |
| `TD-49`だけ先に直し、`TD-50`は後で直す | 前提5により、campaignが2回無効になる。`V-12B → V-12D`は人が15分操作する区間であり、**やり直しの費用を2回払うことになる**（[`TD-45`](../../TODO.md#td-45-campaign-manifestの確定遷移が自分を無効化する不整合を直す)手順4で同じ判断をしている） |

## 理由

2つあります。

第一に、**`V-12E`で確かめたいのは画面ではなく導線です。** 合格条件は「別の認証commandや追加のYes/No確認を挟まず、利用者の認証固有操作をAtCoder loginだけにする」ことです。人が手でURLを開いて代用すると、確かめたい性質そのものが失われます。表示だけを揃えて合格にすると、**通ったことにはなるが、何も分からない記録が残ります。**

第二に、**不足が分かった時点が、直すべき時点です。** 前提7のとおり、この不足は`TD-37`から存在していました。1回目と2回目は手前で止まったため現れず、3回目で初めて到達しました。ここで`V-12`を「`V-12E`以外は合格」と記録して先へ進むと、**`TD-38`以降の認証設計が、成立を確認していない導線を前提に進みます。**

## 影響と再評価条件

- **3回目のcampaignの`V-12A`・`V-12B`・`V-12C`・`V-12D`の合格は、修正をもって取り消されます。** 記録は[`v12-02`](../verification/judge-adapter/results/2026-09-20-v12-02.md)に残します
- **人の操作が要る`V-12B → V-12D`を、もう一度15分やり直すことになります。** 4回目は`TD-49`と`TD-50`をまとめて直してから開始します
- **Chrome Web Storeの再審査は発生しません。** 決定2により拡張機能のsourceを変えないためです。配信中の`0.1.1`をそのまま使い続けます
- `V-12E`の入口は検証物であり、製品コードではありません。**製品の`submit`実装へ流用しません**

次のいずれかが起きたら見直します。

- **入口をhelperへ実装すると、拡張機能の変更が避けられないと分かったとき。** CWS再審査の期間を含めた計画へ組み直します
- **提出確認画面への遷移が、Bot対策の回避なしには成立しないと分かったとき。** `V-12E`の不合格として扱い、回避策を足さずに方式Aの再設計へ戻します（[`TD-40`](../../TODO.md#td-40-提出ページのcontent-scriptとturnstileの共存を検証する)と同じ判断基準）
