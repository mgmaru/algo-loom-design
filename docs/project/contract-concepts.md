## ドキュメント概要

本書は、AlgoLoomの設計文書で使う「契約」という言葉を、法律用語やコード上のインターフェースだけに限定せず、平易に説明します。製品契約、Core契約、保存契約、境界の契約、契約テスト等が何を表し、目的、機能、要件、実装、テストとどう関係するかを定義します。

本書は個別機能の新しい契約を決める正本ではありません。具体的なMVP範囲は[MVPスコープ](../product/mvp.md)、Coreの不変条件は[Core契約](../architecture/core-contracts.md)、実装向けの規範は[`spec/`](../../spec/README.md)を優先します。

## 0. 結論

AlgoLoomの文書でいう「契約」は、次の意味です。

> 実装方法や内部構造が変わっても、製品または部品が必ず守らなければならない約束事。

法律上の契約ではありません。利用者、設計者、実装者、テスト作成者が、次のことを同じ意味で理解するための技術上の約束です。

- どの入力を受け付けるか。
- どの条件で操作を実行するか。
- 成功した場合に何が成立するか。
- 何をしてはならないか。
- 失敗した場合に何が残るか。
- 同じ操作を再実行してよいか。
- どのデータや状態を信頼してよいか。

今後「契約」という言葉が分かりにくい場合は、まず「実装が必ず守る約束事」と読み替えます。

## 1. なぜ「契約」と呼ぶのか

### 1.1. ATMの例

ATMで1万円を振り込む操作を考えます。利用者は、内部で使われているプログラミング言語、クラス、データベースのテーブルを知る必要はありません。一方、次のことは信頼できなければなりません。

- 指定した相手へ1万円が振り込まれる。
- 自分の残高からは1万円だけ減る。
- 同じ操作が勝手に2回実行されない。
- 通信が切れた場合、振り込まれたか確認できる。
- 完了していない処理を「完了」と表示しない。

これらが契約です。

内部の言語やDBを変更しても、この約束を維持する必要があります。反対に、内部コードがきれいで処理が高速でも、同じ振り込みが2回行われるなら契約を守っていません。

### 1.2. 契約という言葉が表す強さ

「仕様」は、画面、名称、対応環境、実装方式、例示等を広く含められます。その中で「契約」と呼ぶのは、次の強さを区別するためです。

> 内部を作り替えても、この約束は破ってはならない。

契約は、現在のコードが偶然そう動いているという事実とは異なります。維持する理由があり、設計として明示され、実装とテストを拘束する約束だけを契約として扱います。

## 2. 契約を構成するもの

契約は、正常系の結果だけではありません。少なくとも次の要素から構成されます。

| 要素 | 確認する問い |
|---|---|
| 入力 | 何を受け付け、何を拒否するか |
| 前提条件 | 実行前に何が成立している必要があるか |
| 操作 | 何を対象に、どの作用を実行するか |
| 事後条件 | 成功した後に何が成立するか |
| 禁止事項 | 成功させるためでも、何をしてはならないか |
| 外部作用 | 通信、提出、削除、ブラウザ起動等がいつ起きるか |
| 失敗時の状態 | どこまで完了し、何が保存されているか |
| 回復 | 再実行してよいか、次に何をするか |
| 不変条件 | どの処理やバージョンでも崩してはならない性質 |
| 検証方法 | 約束を守っていると、どのテストや確認で判断するか |

例えば「問題を取得できる」だけでは、契約として不十分です。既存ソースコードがある場合、通信が途中で切れた場合、同じ操作を再実行した場合まで定めることで、実装者と利用者が同じ意味を共有できます。

## 3. 目的・機能・要件・契約・実装・テストの関係

これらの言葉は近い意味を持ちますが、主に答える問いが異なります。

| 言葉 | 主に答える問い | 例 |
|---|---|---|
| 目的 | なぜ作るのか | 学習中の変化を後から振り返れるようにする |
| 機能 | 何ができるのか | チェックポイントを保存できる |
| 要件 | 何を満たす必要があるか | 明示操作で保存済みソースコードを記録する |
| 契約 | 実装が変わっても何を守るか | 保存後のソーススナップショット本文を上書きしない |
| 実装 | どう実現するか | SQLiteへトランザクションで保存する |
| テスト | 約束を守っているとどう確認するか | 作業ファイルの変更後も以前のスナップショットが変わらないことを確認する |

要件は「必要なこと」全般を広く表します。その中でも、実装方式やバージョンが変わっても維持すべき安定した要件を、本書では特に契約と呼びます。

```mermaid
flowchart LR
    P[目的<br/>なぜ作るか] --> F[機能<br/>何ができるか]
    F --> R[要件<br/>何を満たすか]
    R --> C[契約<br/>何を守り続けるか]
    C --> I[実装<br/>どう実現するか]
    C --> T[テスト<br/>どう確認するか]
    I --> T
```

## 4. AlgoLoomにおける契約の例

### 4.1. `get`の契約

`get`には、「問題を取得する」以外にも次の約束があります。

- 利用者が指定した一問だけを取得する。
- 公開入出力例を保存する。
- 選択した一言語のテンプレートだけを作る。
- 既存の編集済みソースコードを上書きしない。
- 同じ操作を再実行しても重複を増やさない。
- 途中で失敗した場合、安全に再実行できる。
- 問題本文、解説、非公開テストを保存しない。

コマンドが終了コード`0`を返しても、既存ソースコードを上書きしたなら契約違反です。契約は「動いたか」だけでなく、「何を守りながら動いたか」を含みます。

### 4.2. `test`の契約

`test`には次の約束があります。

- 利用者が選んだ保存済みソースコードを実行する。
- 公開入出力例と比較する。
- コンパイルエラー、実行時エラー、タイムアウト、出力量超過、不一致を区別する。
- タイムアウトと取消の後に対象のプロセスツリーを残さない。
- 入出力例の通過をAtCoder上のACと表示しない。
- 利用者のコードを自動修正しない。

プロセス制御を一つのクラスへ置くか複数のモジュールへ分けるかは実装判断です。タイムアウト後にプロセスツリーを残さないことは契約です。

### 4.3. `submit`の契約

`submit`には次の約束があります。

- 利用者の明示操作なしに提出しない。
- 問題、言語、ソースコード、アカウントを送信前に確認する。
- 送信するソーススナップショットと提出意図を送信前に耐久保存する。
- 送信されたか不明な場合、自動で再送しない。
- 提出IDを取得した後は、同じIDで判定を確認する。
- 判定ポーリングのタイムアウトを提出失敗と表示しない。
- 別のAtCoderアカウントを検出した場合は送信前に停止する。

通信が切れたとき、失敗とみなして自動再送する実装は便利に見えても契約違反です。最初の提出がAtCoderへ届いている可能性があるためです。

### 4.4. 履歴とスナップショットの契約

- 編集中ソースコードの権威は、作業領域の通常ファイルである。
- チェックポイントと提出スナップショットは、保存後に本文を上書きしない。
- 判定は、取得時刻付きの観測として保存する。
- 問題チェックアウトを削除しても、保存済み履歴を自動削除しない。
- 同じ問題の解き直しは、新しい`SolveAttempt`として保存する。

SQLiteのテーブル名やカラム名を変更しても、この意味と不変条件を維持できるなら契約は変わりません。

## 5. 契約の種類

### 5.1. 製品契約

利用者に対して製品全体が守る約束です。

- 明示操作なしに提出しない。
- 既存ソースコードを上書きしない。
- オフラインで履歴を閲覧できる。
- AI、クラウド、特定エディタをCoreの必須条件にしない。

### 5.2. Core契約

Coreの複数機能が共通して守る約束です。

- 成功済みのデータを失わない。
- 部分失敗時に、完了済み、未完了、保持データ、次の操作を示す。
- 無期限に待たない。
- 外部作用をローカル処理と区別する。
- 任意機能の失敗でCoreの成功状態を変えない。

### 5.3. データ契約

保存するデータの意味、関係、状態、不変性に関する約束です。

- `SolveAttempt`は一度の解答試行を表す。
- `FocusInterval`は一つの能動的な時間区間を表す。
- ソーススナップショットは保存後に不変である。
- 欠損した時間やメモリを`0`または推測値で補わない。
- 判定待ちから最終判定への進行を、ソーススナップショットの上書きとして扱わない。

### 5.4. 保存契約

データを作成、更新、読み出し、移行、持ち出す際の約束です。

- 一回の業務操作に必要な更新をトランザクション化する。
- マイグレーション前に復旧可能な退避を作る。
- 未知の将来スキーマを推測して書き換えない。
- エクスポートへ秘密情報と不要な絶対パスを含めない。
- エクスポートからAlgoLoomなしでソースコードを回収できる。

### 5.5. 境界の契約

各部品が担当することと、担当しないことの約束です。

| 境界 | 担当すること | 担当しないこと |
|---|---|---|
| `LanguageProfile` | テンプレート、ツールチェーン診断、`BuildPlan`、`RunPlan` | OS固有のプロセス終了、AtCoder通信、DB保存 |
| `HostPlatform` | OS固有のプロセス、パス、ターミナル、ファイル操作 | 言語テンプレート、提出言語、履歴の意味 |
| `JudgeAdapter` | 問題取得、アカウント確認、提出、判定 | ローカルコンパイラの探索、履歴スキーマ |
| `HistoryStore` | トランザクション、履歴状態、クエリ | ソースコードのビルドと実行 |
| `BrowserLauncher` | OSへのURL起動要求 | ページ読み込み、ログイン、閲覧完了の判定 |

境界の契約は、コード上のメソッド名だけではありません。責任を越えて何をしてはならないかも含みます。

### 5.6. 安全性の契約

- 外部入力からシェルコマンド文字列を組み立てない。
- 秘密情報を作業領域、履歴DB、エクスポート、通常ログへ保存しない。
- 秘密情報保管庫を利用できない場合、平文ファイルへ自動的に切り替えない。
- 送信状態不明では無条件に再送しない。
- 安全性を確認できない操作だけを安全側で停止する。

### 5.7. 回復の契約

- 同じ操作の再実行で、既存ソースコード、履歴、外部提出を重複・破壊しない。
- 部分失敗時は、成功済みの結果を失敗扱いにしない。
- 状態不明を成功または未実行と推測しない。
- 再実行が安全でない場合は、確認方法と次の安全な操作を示す。
- プロセス強制終了後も、耐久保存済みの状態を確認できる。

### 5.8. 契約テスト

契約テストは、実装を差し替えても同じ約束を守ることを確認する共通テストです。

例えば、C++、Python、Go、Rustの各`LanguageProfile`へ、次の同じテストを適用します。

- `BuildPlan`と`RunPlan`がシェル文字列を含まない。
- ツールチェーン不足を共通の分類で返す。
- 一言語分のテンプレートだけを作る。
- 生成物と後始末の責任が明確である。

各実装が異なる内部コードを持っていても、共通テストへ合格すれば、同じ境界の契約を満たす証拠になります。

## 6. 契約ではないもの

### 6.1. 法律上の契約ではない

本書の契約は、利用規約、ライセンス、外部サービスとの法的な合意を意味しません。技術設計上の約束です。

### 6.2. 現在の挙動すべてではない

現在の実装が偶然返している文字列、並び順、処理時間等を、理由なくすべて契約として固定しません。維持する必要がある挙動と、変更できる実装詳細を区別します。

### 6.3. インターフェース定義だけではない

型、メソッド名、引数、戻り値は契約の一部になり得ますが、それだけでは不十分です。失敗時の状態、外部作用、禁止事項、再実行方法も契約に含まれます。

### 6.4. テストそのものではない

契約は守るべき約束で、テストはその証拠を得る方法です。

例えば契約が「タイムアウト後にプロセスツリーを残さない」であれば、テストでは子プロセスを起動するプログラムを意図的にタイムアウトさせ、終了後に残っていないことを確認します。

テストが存在するから契約になるのではありません。先に守るべき契約があり、その契約を検証するためにテストを作ります。

### 6.5. 実装を一つに固定するものではない

契約は実装の自由をなくすためのものではありません。同じ約束を守れる複数の実装方法を許すための境界でもあります。

SQLiteのテーブル構成を変更しても、履歴の意味、不変性、回復方法を維持できれば契約を守っています。反対に、コード量が少なくても、既存ソースコードを上書きするなら契約違反です。

## 7. 契約の書き方

契約は、実装者が推測せず、テスト作成者が合否を判定できる形で書きます。

### 7.1. 良くない例

```text
安全に問題を取得する。
適切にエラーを処理する。
履歴を分かりやすく表示する。
```

「安全」「適切」「分かりやすい」の条件が分からないため、実装者とレビュー担当者が異なる意味で解釈できます。

### 7.2. 契約として判断できる例

```text
同じ問題を同じ場所へ再取得しても、編集済みソースコードを上書きしない。
送信開始後に応答を確認できない場合は、送信状態不明として保存し、自動で再送しない。
履歴一覧はローカルDBだけから取得し、AtCoderへの通信を必要としない。
```

何を満たすか、何をしてはならないか、どう検証するかを判断できます。

### 7.3. 契約を書くときの確認事項

- 正常時だけでなく、拒否、中断、タイムアウト、部分失敗を書く。
- 「しない」「含めない」「推測しない」等の禁止事項を書く。
- 成功済みの状態と未完了状態を区別する。
- 値の意味、単位、取得元、欠損の扱いを書く。
- 外部作用を始める前に必要な保存と確認を書く。
- 検証可能な完了条件または受け入れシナリオへ対応付ける。
- クラス名、テーブル名等の実装詳細を、必要なく製品契約へ含めない。

## 8. 契約か実装判断かを見分ける方法

次の問いのいずれかが「はい」であれば、契約に関わる可能性が高いと判断します。

1. 変更すると、利用者が同じ操作の後に異なる行動を選ぶか。
2. 変更すると、同じ結果または保存値を別の意味で読む必要があるか。
3. 変更すると、外部通信、提出、削除、秘密情報の扱いが変わるか。
4. 変更すると、失敗後に再実行してよいかどうかが変わるか。
5. 変更すると、既存データを新しいバージョンで同じ意味として扱えないか。
6. 変更すると、対応環境、対象利用者、必須依存が変わるか。

すべて「いいえ」で、二つの実装が同じ受け入れ条件を同じ結果で満たせるなら、実装リポジトリのADRで決められる可能性が高いと判断します。詳しい境界は[製品契約と実装判断の境界](product-contract-and-implementation-boundary.md)を参照します。

## 9. 契約を変更する場合

契約は変更禁止ではありません。利用者検証、外部サービスの変更、実装上の発見によって、より適切な契約へ変更できます。ただし、コードだけを先に変更しません。

AlgoLoomでは、次の順序で扱います。

1. 変更する約束と、変更が必要な理由を特定する。
2. 利用者、保存データ、外部作用、安全性、回復、既存バージョンへの影響を確認する。
3. 正本となる`docs/`の設計文書を更新する。
4. 同じ変更で影響する`spec/`を更新する。
5. 受け入れ条件とテストを更新する。
6. 確定した`spec/`を実装リポジトリへ再同期する。
7. 実装を変更する。

実装中に契約変更の必要が判明した場合、実装リポジトリのADRだけで確定せず、設計リポジトリへ変更提案を戻します。

## 10. 読み替え一覧

今後、設計文書で次の言葉を見た場合は、まず次のように読み替えます。

| 用語 | 平易な読み替え |
|---|---|
| 製品契約 | 利用者に対して製品が必ず守る約束事 |
| Core契約 | Coreのどの機能でも共通して守る約束事 |
| データ契約 | 保存する値、関係、状態の意味に関する約束事 |
| 保存契約 | データの保存、更新、移行、持ち出しで守る約束事 |
| 境界の契約 | 各部品が担当すること、担当しないことの約束事 |
| 安全性の契約 | 危険な作用と秘密情報を安全に扱う約束事 |
| 回復の契約 | 失敗後に残る状態と、安全に戻る方法の約束事 |
| 契約テスト | 実装を差し替えても約束を守ることを確認する共通テスト |

「この判断は製品契約に関わる」という表現は、次の意味です。

> その判断を変えると、利用者または実装の別部分が信頼している約束が変わるため、局所的な実装の都合だけでは決められない。

## 12. 最終方針

AlgoLoomにおける契約は、設計を難しくするための形式ではありません。実装方法を自由に変えながら、利用者のソースコード、学習履歴、外部提出、安全性、失敗からの回復について、変えてはいけない約束を共有するためのものです。

契約を明確にすると、実装者は「何を変えてよいか」を判断でき、テスト作成者は「何を確認すべきか」を判断でき、利用者は「何を信頼してよいか」を判断できます。
