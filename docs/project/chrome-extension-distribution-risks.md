## ドキュメント概要

本書は、`TD-09`で候補Aを選定した時点の比較軸に含まれていなかった**運用開始後のリスク**を記録します。導入時点の安全境界ではなく、更新、障害、配布停止という時間軸の問題を扱います。

## 0. 結論

方式Aは、AlgoLoom本体（PyPI）と認証用Chrome拡張機能（Chrome Web Store）の2つで成立します。このうち**拡張機能の版と可用性はAlgoLoomが制御できません**。ここから3つのリスクが生じます。

| # | リスク | 深刻度の要点 |
|---|---|---|
| 1 | 更新の非対称性 | 拡張機能はChromeが全利用者へ自動更新し、開発者は停止も版の固定もできない。CLIは利用者が更新するまで古い |
| 2 | 外部への可用性依存 | 審査の所要時間を制御できず、掲載が失われると利用者側へ警告が表示される |
| 3 | 変更頻度と制御権の逆転 | 最も頻繁に更新が必要な部品（AtCoder追随）が、最も制御できない経路に乗っている |

2026年8月26日に、緩和策**H**（AtCoder依存部分を拡張機能から追い出す）と緩和策**D**（縮退運転）の採用を決定しました。設計内容は[拡張機能の責任境界と提出の縮退運転設計](../features/extension-boundary-and-degraded-submission.md)を正とします。

**「配布経路が2つで利用者の手間が増える」ことは、これらに比べれば小さい問題です。** 初回に1回、AlgoLoomが開いた掲載ページで追加を承認するだけであり、利用者の継続的な負担にはなりません。本書が扱うのは経路の数ではなく、**制御権の所在**です。

## 1. 前提

| 配布物 | 配布経路 | 版を決める主体 | 可用性を決める主体 |
|---|---|---|---|
| AlgoLoom本体（認証ヘルパーを含む） | PyPI | **AlgoLoom**（利用者が更新操作を行う） | **AlgoLoom** |
| 認証用Chrome拡張機能 | Chrome Web Store | **Chrome**（自動更新） | **Google**（審査・掲載） |

右2列が食い違っていることが、本書のすべてのリスクの原因です。

## 2. リスク1: 更新の非対称性

### 2.1. 確認した事実

| # | 事実 | 出典 |
|---|---|---|
| 1 | Chrome Web Storeで配布する拡張機能はChromeの更新機構で更新され、開発者はこれを制御できない | [更新手順](https://developer.chrome.com/docs/webstore/update) |
| 2 | 企業向けのバージョン固定は、visibilityが`Unlisted`または`Private`（Trusted Testers）の場合は利用できない | [バージョン固定](https://support.google.com/chrome/a/answer/11190170) |
| 3 | ロールバックは旧版を新しいバージョン番号で再公開する操作であり、それも通常の自動更新で全利用者へ配られる | [ロールバック](https://developer.chrome.com/docs/webstore/rollback) |

事実2は`V-12`の配布形態そのものに関わります。**限定公開を選ぶ限り、版の固定という回避策は最初から存在しません。**

### 2.2. 影響

```text
拡張機能  CWSが全利用者へ即座に配る        AlgoLoomは止められない
CLI       利用者が更新操作を行うまで古い    AlgoLoomは強制できない
              ↓
「新しい拡張機能 + 古いCLI」という組み合わせが定常的に発生する
```

[AtCoder認証設計 §3.1.5](../architecture/atcoder-authentication.md#315-次の実機検証へ渡す条件)は「審査済みの拡張機能識別子、版、権限、配布元を固定し、想定外の版または権限なら認証を開始しない」としています。この条件を**厳密な版の一致**として実装すると、拡張機能が更新された瞬間に、更新していないすべての利用者の認証が停止します。

### 2.3. 厳密な版固定は検証要件であり、製品要件ではない

`V-12`は再現性のために対象版を一つへ固定します。これは検証キャンペーンの要件です。**製品がこれをそのまま引き継ぐ理由はありません。** 両者を区別せずに実装すると、上記の停止が製品仕様になります。

### 2.4. 緩和策の候補

| # | 緩和策 | 内容 |
|---|---|---|
| A | 固定する対象を分ける | **固定**するのは拡張機能識別子、権限セット、配布元。**交渉**するのは通信protocol版。拡張機能の厳密なバージョンは固定しない |
| B | 後方互換の責任を拡張機能側へ置く | 拡張機能は常に先に更新される。したがって**新しい拡張機能が古いCLIと話せる**ことを契約とする。拡張機能は現行protocol版とその一つ前を話せるようにし、予告なく古いprotocolを落とさない |
| C | 権限セットの変更を設計変更として扱う | Chromeでは要求権限が増えると利用者の再承認が必要になり、承認まで機能が停止する。権限の追加は修正リリースではなく、設計判断としてやり直す |

緩和策Aは、`bootstrap_ready`が既に`protocol_version`を送っているため、追加の仕組みを必要としません。

## 3. リスク2: 外部への可用性依存

### 3.1. 確認した事実

| # | 事実 | 出典 |
|---|---|---|
| 1 | すべてのitemが審査対象であり、権限や変更内容によって所要時間が延び得る。visibilityを変えても審査は同じ | [審査プロセス](https://developer.chrome.com/docs/webstore/review-process)、[Distribution設定](https://developer.chrome.com/docs/webstore/cws-dashboard-distribution) |
| 2 | Chrome 117以降、インストール済みの拡張機能がChrome Web Storeから消えた場合、Chromeは利用者へ警告を表示する。開発者による取り下げと、ポリシー違反による削除の両方が対象になる | [Chromeが無効化した拡張機能の管理](https://support.google.com/chrome_webstore/answer/2811969) |
| 3 | malwareと判定された拡張機能は自動的に無効化される | 同上 |

### 3.2. 影響

- **復旧時間を自分で決められません。** AtCoder側の変更に追随する修正版を出したいとき、公開までの時間は審査に依存します
- **取り下げは利用者に見えます。** 事実2により、掲載が失われると既存利用者のChromeに警告が出ます。拡張機能自体は動き続けますが、利用者は「削除を推奨されるソフトウェア」として認識します
- **malware判定を受けた場合は即座に停止します**（事実3）

認証情報を読み取って端末内へ渡す拡張機能は、審査で最も厳しく見られる形です。単一目的、最小権限、privacy開示は[CWS配布準備 §3](../verification/judge-adapter/v12-chrome-web-store-preparation.md)で満たしていますが、**判定はAlgoLoomの側にありません**。

### 3.3. 停止手段としてのunpublishに副作用がある

[CWS配布準備 §6](../verification/judge-adapter/v12-chrome-web-store-preparation.md)は「新規標準追加を止める手段をunpublishに固定する」としています。事実2により、**この操作は既存利用者への警告表示を伴います**。

`V-12`の検証は利用者が検証owner本人だけなので影響は限定されますが、製品の配布停止手順としてそのまま採用すると、利用者へ予告なく警告が出ることになります。停止手順は、対象利用者が残っているかどうかで区別する必要があります。

限定公開（`Unlisted`）のitemが事実2の警告対象になるかは未確認です。掲載自体は存在するため対象外である可能性がありますが、推測で判断しません。

### 3.4. 緩和策の候補

| # | 緩和策 | 内容 |
|---|---|---|
| D | 縮退運転を設計へ入れる | 拡張機能が使えない場合に、利用者が公式サイトで手動提出し、AlgoLoomが結果を履歴へ残せる経路を用意する。§4を参照 |
| E | 拡張機能へ入れる機能を最小化する | 審査の対象面積と、更新が必要になる頻度の両方を下げる |
| F | ソースを公開し、掲載から参照できるようにする | 監査可能性を審査へ示す |
| G | 停止手順を利用者の有無で分ける | 利用者が残っている状態でのunpublishを既定の停止手段にしない |

## 4. リスク3: 変更頻度と制御権の逆転

### 4.1. 問題

[AtCoder認証UX設計 §3.2](atcoder-authentication-manual-operation-automation.md)は「認証後は同じブラウザで対象、言語、ソースコードを準備し」としています。CDPとWebDriverを使わない以上、これを行うのは拡張機能です。

つまり拡張機能は**AtCoderの提出フォームの構造に結合**します。[`F-SUBMIT-05`](../../spec/features.md#85-atcoder側の変更検知と互換性確認f-submit-05)が扱っているとおり、AtCoder側の構造は変わり得ます。

```text
変更頻度が高い          制御権
─────────────────────────────────────────
AtCoder追随（提出フォーム）  → 拡張機能 → Chrome Web Store（他者）
機能追加・改善               → CLI      → PyPI（AlgoLoom）
```

**最も頻繁に更新が必要な部分が、最も制御できない経路に乗っています。** これがリスク1とリスク2を増幅します。

### 4.2. 既に設計されている緩和

[`F-SUBMIT-05` R6](../../spec/features.md#85-atcoder側の変更検知と互換性確認f-submit-05)により、AtCoder側の変更を検出したときは**提出だけを安全側で停止し、ローカルテスト、履歴閲覧、エクスポートは継続**します。したがってAtCoderの変更が製品全体を止めることはありません。

残る問題は**提出機能の復旧時間**であり、それが審査に依存することです。

### 4.3. 緩和策の候補

| # | 緩和策 | 状態 | 内容 |
|---|---|---|---|
| H | AtCoder依存部分を拡張機能から追い出す | **採用**（2026年8月26日） | 拡張機能は操作の**種類**と**対象ページ**を固定し、変わりやすい要素の指定だけを認証付き折返し通信で受け取る。AtCoder追随がPyPI側の更新で済む |
| I | 拡張機能を認証だけに限定する | 不採用 | 一往復UXと「copy-and-pasteを求めない」条件（[`F-SUBMIT-01` R10](../../spec/features.md#81-atcoder認証状態確認f-submit-01)）を満たす代替手段がない |

緩和策Hには審査上の危険があります。汎用的なDOM操作の入口にすると、単一目的と最小権限の説明が成立しなくなります。**対象ページ、操作の種類、要求権限を拡張機能側で固定し、認証ヘルパーから変更できないようにすることが採用の条件です。** 固定する項目は[拡張機能の責任境界と提出の縮退運転設計 §2.3](../features/extension-boundary-and-degraded-submission.md#23-拡張機能側で固定する項目)を正とします。

あわせて、拡張機能が`/settings`のHTMLからアカウント識別情報を読む処理を認証ヘルパーへ一本化します。現在は同じ確認を2回行っており、拡張機能側だけがHTML構造に結合しています（[§2.4](../features/extension-boundary-and-degraded-submission.md#24-アカウント照合を認証ヘルパーへ一本化する)）。

## 5. 縮退運転（緩和策D、採用）

> 2026年8月26日に採用を決定。設計内容は[拡張機能の責任境界と提出の縮退運転設計 §3](../features/extension-boundary-and-degraded-submission.md#3-提出の縮退運転)を正とします。

現在の設計には「拡張機能が使えない」場合の提出手段がありません。これがリスク2を単一障害点にしています。

[AtCoder認証設計 §8](../architecture/atcoder-authentication.md#8-採用しない前提と方式)が不採用としているのは「可視browser経路が成立しない場合の、**sessionを用いた直接HTTP提出**へのfallback」です。**利用者自身が公式サイトで手動提出する経路は、この不採用条件に含まれません。**

想定する縮退運転は次のとおりです。

- AlgoLoomはソースコードを準備し、対象問題の公式提出ページをブラウザで開く
- 利用者が自分で内容を入力し、Turnstileと提出操作を行う
- AlgoLoomは提出を自動化せず、判定も推測しない
- 履歴には、縮退運転による提出であることを区別して記録する

これがあれば、Chrome Web Storeが利用できなくなっても**利用者の学習は止まりません**。

ただし、縮退運転を用意するだけでは機能しません。次の3つを設計へ含めることを採用の条件とします。

| # | 条件 | 理由 |
|---|---|---|
| 1 | **縮退のレベルを分ける** | 「連携できない」を一括りにすると、残せる履歴まで捨てる。認証が生きている場合は提出IDと判定を通常どおり取得できる |
| 2 | **事前に検知する** | 拡張機能の有無、版、権限はブラウザ起動前のテンプレート検査で判定できる。「開いたのに何も起きない」を作らない |
| 3 | **自動でフォールバックしない** | 外部作用を利用者の明示操作へ結び付ける契約に従う |

検知機構は新しく作りません。認証付き折返し通信のprotocolが既に状態機械とタイムアウトを持ち、停止理由を返します。足りないのは**停止理由を利用者向けの原因分類と一手へ写像する層**だけです。詳細は[同 §3.4](../features/extension-boundary-and-degraded-submission.md#34-停止理由から原因分類と次の一手への写像)を参照します。

## 6. Firefox + AMO自己配布を採用しない判断

`TD-09`の候補Cは、本書のリスク1とリスク2を構造的に解消します。

| 性質 | 内容 |
|---|---|
| 署名 | 無料。最大24時間、原則自動 |
| 自動更新 | `update_url`を持たない自己配布アドオンは自動更新されない。**版はAlgoLoomが同梱したもので固定される** |
| 導入方法 | ファイルからの追加が公式に文書化されている。**PyPIパッケージへ同梱でき、配布経路が1つになる** |

出典: [自己配布](https://extensionworkshop.com/documentation/publish/self-distribution/)、[署名と配布の概要](https://extensionworkshop.com/documentation/publish/signing-and-distribution-overview/)

**それでも採用しません。** 理由は、Firefoxの導入率を考えると、多くの利用者へ普段使わないブラウザの新規インストールを求めることになるためです。これは[README](../../README.md)の「AlgoLoomをユーザーの環境になじませ、ユーザーの環境をAlgoLoom向けに作り替えない」という原則に反します。**運用上の利点よりも、製品原則を優先します。**

ただし次を認めた上での判断とします。

- Chromeも同様に前提環境であり、Chromeを持たない利用者には同じ負担が生じます。原則は既に一部妥協しており、差は程度の問題です
- 本書のリスク1とリスク2は、緩和はできても構造的には解消されません

したがって、**拡張機能のソースはWebExtensions共通仕様の範囲で書き、Chrome固有APIへ依存させません**（緩和策J）。将来この判断を見直す場合に、書き直しではなくパッケージングの変更で済むようにします。現時点の追加コストはほぼありません。
