## ドキュメント概要

本書は、AtCoder認証の利用者導線だけを定義します。セッション取得、本人確認、保管、失効、OS差および検証gateは[AtCoder認証設計](../architecture/atcoder-authentication.md)を正本とします。

旧導線との比較は残しません。現在採用する導線、手動で残す操作、自動化する処理だけを示します。

## 0. 結論

明示ログインは次の一往復で完了させます。

```text
$ aloom auth login
  → ブラウザでAtCoderへログイン
  → AlgoLoomが本人確認・保存・後始末
  → CLIへ認証済みアカウントを表示
```

初回だけ、利用委譲への同意と署名済み拡張機能の追加・権限承認が加わります。利用者の既存Chromeプロファイルへ触れないため、この初回例外は残します。

| 場面 | 利用者が行うこと | 認証固有の追加操作 |
|---|---|---:|
| 初回セットアップ | `aloom auth login`、初回同意、拡張機能追加、AtCoderログイン | 初回同意と拡張機能追加 |
| 明示的な再ログイン | `aloom auth login`、AtCoderログイン | AtCoderログインだけ |
| `submit`中の再認証 | `aloom submit`、AtCoderログイン、最後の提出操作 | AtCoderログインだけ |
| 有効なセッションでの提出 | `aloom submit`、最後の提出操作 | なし |

すべての場面で、CLIからブラウザへ1回移り、完了後にCLIへ戻る一往復とします。ブラウザ表示中にCLIへ戻ってURL、code、commandまたはCookieを入力させません。

## 1. UX契約

### 1.1. 共通導線

1. 利用者が`aloom auth login`または`aloom submit`を実行する。
2. AlgoLoomが必要な事前確認を行い、ブラウザを開く理由と中止方法をCLIへ表示する。
3. 可視の専用Chromeを前面で開き、利用者が担当する画面へ直接移動する。
4. 利用者はAtCoderの資格情報、追加確認、Turnstileと、提出時の最後の提出操作だけをブラウザで行う。
5. AlgoLoomが導入検出、セッション限定取得、本人確認、保存、後始末を自動で行う。
6. CLIへ結果と、必要な場合だけ次に行える一つの操作を表示する。

CLIは待機中に次の段階だけを表示し、秘密値や内部通信の詳細を表示しません。

```text
ブラウザを開いています
AtCoderへのログインを待っています
アカウントを確認しています
認証情報を保存しています
```

### 1.2. 手動で残す操作

| 操作 | 頻度 | 残す理由 |
|---|---|---|
| 利用委譲への同意 | 初回、取得対象・用途・保存先・権限の変更時 | AlgoLoomがセッションを扱う目的と保存先を説明する |
| 拡張機能追加と権限承認 | 初回、権限変更またはテンプレート再作成時 | Chromeの標準的な利用者承認を維持する |
| AtCoderログインと追加確認 | 初回・失効時 | 資格情報をAlgoLoomへ渡さず、Bot対策を自動化しない |
| 最後の提出操作 | 提出ごと | 外部作用を利用者の明示意思へ結び付ける |

初回同意は毎回確認しません。同意内容へ版を持たせ、同じ内容なら再認証時に再表示しません。

### 1.3. 自動化する処理

- 対応Chromeの検出と専用データディレクトリでの起動
- 初回のChrome Web Storeページ表示
- 拡張機能の固定ID・版・権限・配布元の確認と導入完了検出
- 初期化とAtCoderログインページへの遷移
- 対象Cookieの変更検出、一度限りの受け渡し、アカウント本人確認
- OSの秘密情報保管庫への保存と、新しい処理からの再確認
- 認証後の提出確認ページへの遷移
- browser、折返し通信、一時秘密値、実行用一時プロファイルの回収

利用者に初期化ページへ戻らせたり、拡張機能のポップアップを開かせたり、取り込みボタンを押させたりしません。

## 2. 初回セットアップ

初回セットアップもCLIとブラウザの一往復に収めます。

| 順序 | 場所 | 処理 |
|---:|---|---|
| 1 | CLI | 利用者が`aloom auth login`を実行し、取得対象・用途・保存先を確認して初回同意する |
| 2 | ブラウザ | AlgoLoomがクリーンなテンプレート用Chromeで正確なChrome Web Storeページを開く |
| 3 | ブラウザ | 利用者が配布元と権限を確認して拡張機能を追加する |
| 4 | 自動 | AlgoLoomが導入を検出し、テンプレートを確定して実行用一時複製を起動する |
| 5 | ブラウザ | AtCoderログインページへ自動遷移し、利用者がログインする |
| 6 | 自動 | セッションを限定取得し、本人確認、保存、後始末を行う |
| 7 | CLI | 認証済みアカウントを表示する |

Chromeの終了と再起動が内部で必要でも、利用者の操作場所をCLIへ戻しません。テンプレートを安全に確定できない場合は認証を成功扱いせず、AlgoLoom所有領域だけを破棄します。

## 3. `auth login`と`submit`

### 3.1. `aloom auth login`

テンプレートが健全なら、拡張機能追加と利用委譲への同意を繰り返しません。利用者がAtCoderへログインした後は、認証結果を自動で取り込み、本人確認と保存を終えてCLIへ戻ります。

有効なセッションがすでにあり、同じアカウントを確認できる場合はブラウザを開かず、現在の認証済みアカウントを表示して終了できます。

### 3.2. `submit`からの再認証

`submit`は、保存済みセッションが利用不能なら別commandを要求せず、次を表示して認証を継続します。

```text
AtCoderへの再ログインが必要です。ブラウザを開きます。
中止するには Ctrl+C を押してください。
```

初回同意が有効であることを確認した後は、追加のYes/No確認を要求しません。認証後は同じブラウザで対象、言語、ソースコードを準備し、利用者の最後の提出操作へ進みます。認証完了直後にCLIへ戻して再度ブラウザを開く往復を作りません。

初回セットアップが未完了の場合は、同じ一往復の中で初回同意と拡張機能追加から開始します。利用者が中止した場合は提出しません。

## 4. Chromeプロファイルの寿命

| 領域 | 保持物 | 寿命 |
|---|---|---|
| 利用者の既存プロファイル | 利用者の履歴、Cookie、保存パスワード、拡張機能 | AlgoLoomは参照・複製・変更しない |
| クリーンなテンプレート | 署名済みAlgoLoom拡張機能と必要最小限の設定 | 再設定まで。AtCoderのCookie、履歴、入力情報は保持しない |
| 実行用一時複製 | 今回の認証または提出に必要な一時状態 | 正常終了、取消、時間切れ、異常終了後に全体を削除する |

テンプレートの完全性を確認できない場合は推測で修復せず破棄し、次回だけ初回セットアップへ戻します。利用者の既存Chrome、企業向けポリシー、外部拡張設定またはOSレジストリは変更しません。

## 5. 取消・失敗・回復

- CLIの待機中は`Ctrl+C`等の一貫した操作で取消できるようにする。
- browserを閉じた場合も取消として扱い、利用者を責めるerrorにしない。
- 取消、時間切れ、本人不一致、保存失敗では提出を行わず、未確認セッションを破棄する。
- cleanupを確認できない場合は認証または提出だけを停止し、次回開始前にAlgoLoom所有の残存processと一時領域を回収する。
- errorは原因分類、外部送信の有無、影響を受けない機能、次の一つの行動をこの順で示す。
- ローカルtest、履歴、checkpoint等は認証失敗によって停止しない。

## 6. 採用条件

次を3つの対象OSと通常Chromeで確認するまで、実現手段を製品成立済みとは扱いません。

- 初回追加後に手動でページを戻らず、導入完了を検出できる。
- テンプレートの複製、更新、破棄を安全に行える。
- 失効後再認証で、利用者の手動操作がAtCoderログインだけになる。
- `submit`からの再認証と提出が同じブラウザ内で連続する。
- 正常終了とすべての中断点で、既存プロファイルと秘密情報を汚さず一時資源を回収できる。
- CLIとブラウザの移動が一往復で、URL・code・Cookieのcopy-and-pasteや手動のページ探索が発生しない。

検証環境の層とOS差は[AtCoder認証設計 §6.1](../architecture/atcoder-authentication.md#61-検証環境と自動化可能性の境界)を正とします。

## 7. 採用しない短縮方法

- 利用者の既存Chromeプロファイル、保存パスワードまたはCookieを再利用する。
- CDP、WebDriver等でAtCoderログイン、Turnstileまたは最後の提出操作を制御する。
- Chromeの企業向けポリシー、外部拡張設定またはOSレジストリを変更して拡張機能を強制導入する。
- Chrome for Testing、独自Chromiumまたは自動操作用browserを製品runtimeにする。
- 認証付きブラウザ経路が失敗した場合に直接HTTP提出へ切り替える。

これらは操作数を減らせても、既存環境の所有境界、利用者承認、通常ChromeまたはBot対策との互換性を損なうため採用しません。
