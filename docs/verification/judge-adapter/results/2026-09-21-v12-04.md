## ドキュメント概要

この記録は、campaign `v12-2026-09-21-01`で観測した事実と合否を保持します。実際のアカウント名、Cookie、トークン、生のヘッダー、拡張機能の固定ID、listing URL、secret storeのservice ID、絶対pathは含めません。これらはリポジトリ外のowner専用領域にあります。

## 8. `V-12E`が最後の受け渡しに到達しなかった理由

`V-12E`は次の順序を求めます。**成立したのは1〜8で、9で止まりました。**

| # | 求められること | 結果 |
|---:|---|---|
| 1 | `submit`相当の入口が、保存済みlocal sessionが無いことを確認する | 成立 |
| 2 | 再認証の理由、中止方法、対象問題・言語・sourceを表示する | 成立（`reason_shown`、`cancel_method_shown`） |
| 3 | 同じ入口がbrowserを自動起動する | 成立 |
| 4 | 利用者の認証固有操作をAtCoder loginだけにする | 成立。`extra_authentication_commands`と`extra_confirmations`がいずれも0 |
| 5 | 本人照合してsecret storeへ保存する | 成立。項目の存在を独立した観測で確認した |
| 6 | **同じbrowser**で提出確認画面まで進む | 成立（`confirmation_shown`） |
| 7 | 手動ページ探索とcopy-and-pasteを要求しない | 成立。要求していない |
| 8 | 画面のボタンのPOSTをhelperが受理する | **成立。** 4回目の`authentication_rejected`は再発していない |
| 9 | 303で同じtabがAtCoderの提出pageへ着く | **未到達。** browserは`http://127.0.0.1:<待受番号>/submission/proceed`で`ERR_CONNECTION_REFUSED`を表示した |

### 8.1. 観測した事実

| 観測 | 内容 |
|---|---|
| browserの表示 | `http://127.0.0.1:<待受番号>/submission/proceed`で`ERR_CONNECTION_REFUSED`。**提出pageのURLではない** |
| runtime profileの履歴 | 最後の記録が提出確認画面。**AtCoderの提出pageの訪問記録がない** |
| helperの待受 | 停止済み。`serveSubmission`が押下を受理した後の`server.Shutdown`が走っている |
| helper process | 生存。停止せず、Chromeの完全終了を待っていた |
| helperの結果JSON | `ok: true`、`confirmation_shown: true`、`submit_page_redirect_issued: true`、`submission_form_operated: false`、`submitted: false` |

`ERR_CONNECTION_REFUSED`は、browserが**その待受番号へあらためて接続しようとして拒否された**ことを示します。つまりbrowserから見ると、送ったPOSTの応答を受け取れないまま接続が終わり、接続し直したときには待受が閉じていました。helper側から見ると、POSTは受理して303を書いています。**両方とも起きたという事実が、いまの観測です。**

### 8.2. 実測で否定した仮説

最初に立てた仮説は「[`protocol.go`](../../../../scripts/verification/atcoder_v12/helper/protocol.go)が、303を書く**前に**本体へ押下を通知するため、本体の`server.Shutdown`が応答の書き込みに先回りしている」でした。

**この仮説は実測で否定されました。** Goの`http.Server.Shutdown`は処理中のrequestを待つため、通知の順序を変えても応答は届きます。2026年9月21日に、helperと同じ順序をリポジトリ外で再現し、条件ごとに20回ずつ測りました。**外部接続0件です。**

| 再現条件 | 303が届いた回数 |
|---|---|
| 現行の順序（通知 → 303を書く） | **20 / 20** |
| 現行の順序 + browserの先読み接続を模した接続 | 20 / 20 |
| 順序を入れ替え（303を書き切る → 通知） | 20 / 20 |
| 入れ替え + 先読み接続 | 20 / 20 |

**順序の入れ替えでは直りません。** この仮説のまま修正していたら、直っていないものを直したと記録し、人の15分を使う6回目で同じ場所に止まっていました。

**原因はまだ特定できていません。** 特定の手順と、特定できるまで修正しないという判断は[ADR-0013](../../../decisions/0013-find-the-cause-before-fixing-the-v12e-handoff.md)に残しました。

### 8.3. helperが`ok: true`を返したこと

helperは、303を書いた事実を`submit_page_redirect_issued: true`として報告し、全体を`ok: true`で終えました。**helperが観測できるのは303を書いたところまで**であり、この値自体は嘘ではありません（[検証物README](../../../../scripts/verification/atcoder_v12/README.md)）。

ただし**結果JSONだけを見た人は、`V-12E`が成立したと読みます。** 到達しなかったという事実は、人が画面で見たエラーにしか残っていません。これは[`TD-50`](../../../../TODO.md#td-50-helperの誤った成功報告と原因を指せないエラー名を直す)で直した「消したつもりで残る」と同じ型の問題が、別の場所に残っていたということです。[`TD-54`](../../../../TODO.md#td-54-helperの成功報告が到達していないことを覆い隠さないようにする)で直します。

## 9. 次に行うこと

**このcampaignは、原因の特定と修正をもって無効になります。** helperのbuild hashが変わるためで、`V-12A`〜`V-12D`の合格も取り消されます。**記録は消さずに残します。**

6回目のcampaignの前に、[`TD-53`](../../../../TODO.md#td-53-提出確認画面から提出pageへの受け渡しが成立しない原因を特定する)と[`TD-54`](../../../../TODO.md#td-54-helperの成功報告が到達していないことを覆い隠さないようにする)をまとめて片付けます。個別に直すとそのたびにcampaignが無効になり、人が15分操作する`V-12B → V-12D`を何度もやり直すことになるためです（[ADR-0011](../../../decisions/0011-add-submit-entry-before-rerunning-v12.md)決定3と同じ理由）。**拡張機能のsourceは変えないため、CWSの審査・提出・公開は発生しません。**
