## ドキュメント概要

本書は、[Chrome拡張機能配布の運用リスクと緩和策](../project/chrome-extension-distribution-risks.md)が記録した「拡張機能の版と可用性をAlgoLoomが制御できない」という問題に対して、**設計で打てる手**を定義します。緩和策HとDを採用した結果の具体的な設計であり、機能設計がそのまま参照できる粒度で書きます。

## 0. 結論

2つを決定します。

1. **拡張機能には、ブラウザの中でしか実現できない能力だけを置きます。** AtCoder固有の知識はAlgoLoom本体（PyPI）へ置き、AtCoder側の変更へPyPIの更新だけで追随できるようにします。
2. **拡張機能が使えない場合に提出を続ける縮退運転を持ちます。** ただし、検知、通知、利用者の明示操作を伴わない縮退運転は採用しません。

この2つは独立ではありません。1により拡張機能の更新頻度が下がり、2により拡張機能が失われても学習が止まらなくなります。**片方だけでは、[配布リスク §0](../project/chrome-extension-distribution-risks.md#0-結論)の3つのリスクは残ります。**

## 1. なぜこの設計が必要か

| リスク | 本書の対応 |
|---|---|
| 拡張機能は自動更新され、版の固定も停止もできない | §2で拡張機能の更新頻度そのものを下げる |
| 審査と掲載の可用性を制御できない | §3で拡張機能が使えなくても提出を続けられるようにする |
| 変更頻度が最も高い部品が最も制御できない経路にある | §2でこの逆転を解消する |

## 2. 拡張機能の責任境界

### 2.1. 拡張機能でしかできない処理は2つ

方式Aの認証と提出に必要な処理を、「ブラウザの外から行えるか」で分類します。

| 処理 | 拡張機能でしかできないか | 実際に行う場所 |
|---|---|---|
| 同意画面の表示 | いいえ | 認証ヘルパーが`http://127.0.0.1:<待受番号>/bootstrap`で配信する |
| 専用プロファイルでのブラウザ起動 | いいえ | 認証ヘルパー |
| AtCoderのログイン、Turnstile | ― | 利用者 |
| **`REVEL_SESSION`を1件取り出す** | **はい** | **拡張機能**。クッキー操作機能はブラウザの中でしか呼べない |
| `/settings`からアカウント識別情報を読む | いいえ | 認証ヘルパー。クッキーがあれば認証必須ページを取得できる |
| 秘密情報保管庫への保存、新しいプロセスでの再照合 | いいえ | 認証ヘルパー |
| **提出フォームへソースコードと言語を設定する** | **はい** | **拡張機能**。CDP・WebDriverを使わずにページを操作できるのは拡張機能だけ |
| 提出IDの取得 | いいえ | 認証ヘルパー。認証済み通信で読める |
| 判定確認 | いいえ | 認証ヘルパー |
| 最後の提出操作 | ― | 利用者 |

**拡張機能に置くのは、上表で「はい」となる2つだけです。**

### 2.2. 「能力」と「知識」を分ける

残った2つのうち、提出フォームへの設定はAtCoderのページ構造に依存します。ここが最も変わりやすく、そのまま拡張機能へ入れると更新頻度が上がります。そこで責任を次のように分けます。

| 層 | 持つもの | 変更したいときの経路 |
|---|---|---|
| 拡張機能 | **能力**。対象ページ、実行できる操作の種類、要求権限 | Chrome Web Store（審査を伴う） |
| 認証ヘルパー / AlgoLoom本体 | **知識**。どの要素か、どう読むか、いつ止まるか | PyPI（AlgoLoomが決める） |

拡張機能は「何ができるか」を固定し、「どこへ適用するか」だけを認証ヘルパーから受け取ります。これにより、**AtCoderが提出フォームを変えても、追随はPyPI側の更新だけで済みます。**

### 2.3. 拡張機能側で固定する項目

**この固定が安全の要です。** 認証ヘルパーが自由に指定できる範囲を広げると、単一目的と最小権限の説明が成立しなくなります。

拡張機能のソースへ埋め込み、認証ヘルパーからは変更できない項目を次のとおりとします。

| 項目 | 固定する内容 |
|---|---|
| 対象ページ | 認証は`https://atcoder.jp/settings*`、提出は`https://atcoder.jp/contests/*/submit*`のみ。`content_scripts`の`matches`で固定する |
| 実行できる操作の種類 | 「テキストを設定する」「選択肢から値を選ぶ」の2種類のみ。要素の作成、削除、クリック、フォーム送信、スクリプト実行を持たない |
| 受け付ける要素指定 | 形式を検証する。`script`、`iframe`、`style`、`link`、`object`等を対象にできない |
| 要求権限 | `cookies`、`storage`、`https://atcoder.jp/*`、`http://127.0.0.1/*`。増やす場合は修正リリースではなく設計変更として扱う |
| 通信相手 | `127.0.0.1`の動的な待受番号のみ |

指示の受け渡しには新しい通信路を作りません。**拡張機能から認証ヘルパーへ問い合わせる既存の認証付き折返し通信を使います。** 一回限りの秘密値、`Host`、送信元、拡張機能の配布元、本文上限、状態順序の検査は、指示の取得にもそのまま適用します。認証ヘルパーがブラウザへ接続する向きの通信は追加しません。

### 2.4. アカウント照合を認証ヘルパーへ一本化する

現在の検証支援物は、拡張機能が`/settings`のHTMLからアカウント識別情報を読み、`account_checked`として認証ヘルパーへ送っています。認証ヘルパーは、受け取ったクッキーで改めて認証必須ページを取得し、同じ照合を行っています。**同じ確認を2回行っており、拡張機能側だけがHTML構造に結合しています。**

拡張機能から`/settings`のHTML解析を外し、照合を認証ヘルパーへ一本化します。

- **失うもの**: クッキーを渡す前の事前ゲート。利用者が期待と異なるアカウントでログインしている場合、認証ヘルパーが一度クッキーを受け取ってから不一致を検出します
- **許容できる理由**: 認証ヘルパーは受け取った直後、秘密情報保管庫へ保存する前に照合します。[§3.5 取り込みの確定条件](../architecture/atcoder-authentication.md#35-取り込みの確定条件)により、未確認の値は確定保存されません。未確認のクッキーが認証ヘルパーのメモリ上に一時的に存在するだけで、これは現在の設計でも同じです
- **得るもの**: AtCoderのページ構造に依存する解析が1か所になり、その1か所がPyPI側になります

### 2.5. この境界で何が変わるか

| AtCoder側の変更 | 現在の構成 | 本書の構成 |
|---|---|---|
| `/settings`のHTML構造 | 拡張機能とヘルパーの両方を更新。**CWS審査が必要** | ヘルパーのみ。**PyPIの更新だけ** |
| 提出フォームの要素 | 拡張機能を更新。**CWS審査が必要** | ヘルパーのみ。**PyPIの更新だけ** |
| 提出フォームの操作方法そのもの | 拡張機能を更新 | 拡張機能を更新。**CWS審査が必要** |
| 認証・提出の通信protocol | 拡張機能とヘルパーの両方 | 拡張機能とヘルパーの両方。**CWS審査が必要** |

上2行が頻度の高い変更です。**AtCoder追随がCWS審査のクリティカルパスから外れます。**

## 3. 提出の縮退運転

### 3.1. 縮退のレベル

「拡張機能と連携できない」を一括りにすると、残せるはずの情報まで捨てます。壊れている範囲で分けます。

| レベル | 壊れているもの | まだ生きているもの | 利用者が行うこと |
|---|---|---|---|
| `L0` 通常 | ― | すべて | 最後の提出操作だけ |
| **`L1` 提出準備の縮退** | 提出フォームへの自動設定 | 認証、セッション、提出IDの取得、判定確認 | ソースコードの入力と提出操作 |
| **`L2` 認証の縮退** | 拡張機能全体。セッションを取得できない | ローカル機能のみ | 自力でのログインと提出。提出IDは後から照合する |
| `L3` 停止 | 提出経路そのもの | ローカル機能のみ | 提出しない |

`L1`では認証ヘルパーがセッションを持っているため、**提出IDの取得と判定確認は通常どおり行えます。履歴はほぼ完全に残ります。**

AtCoderが提出フォームを変えた場合は`L1`、拡張機能が失われた場合は`L2`です。**原因が違えば、残せるものも、利用者へ伝えるべきことも違います。**

### 3.2. 事前に検知する

**ブラウザが開いたのに何も起きない、という状態を作りません。**

拡張機能の有無、バージョン、権限、テンプレートの完全性は、**ブラウザを起動する前に**AlgoLoom所有のテンプレートプロファイルを検査すれば判定できます。通信protocolの互換性も、テンプレートが持つ拡張機能のバージョンから事前に分かります。

したがって`submit`は、**外部通信を行う前に「今回の提出準備を自動化できるか」を判定します。** できない場合は、ブラウザを開く前に理由と次の一手を示します。この判定は[提出前確認](../../spec/features.md#82-提出前確認f-submit-02)へ追加する項目です。

事前に判定できない失敗（AtCoder側の要素が見つからない等）だけが、ブラウザを開いた後の検知になります。

### 3.3. 自動でフォールバックしない

縮退運転は外部作用を伴います。[Core契約](../architecture/core-contracts.md)の「外部提出、source送信、削除等の作用は、利用者の明示操作なしに行わない」に従います。

- 自動化できないと判定した時点で、その提出操作は`FAILED_BEFORE_SEND`として一度閉じます
- 縮退運転は、利用者の**新しい明示操作**として開始します
- 「提出を自動化できなかったので手動モードでブラウザを開きました」という挙動にしません

### 3.4. 停止理由から原因分類と次の一手への写像

**検知機構を新しく作る必要はありません。** 認証付き折返し通信のprotocolは既に状態機械とタイムアウトを持ち、どの段階で連携が途切れたかを機械可読な停止理由として返します。

```text
初期化待ち → 同意待ち → アカウント確認待ち → クッキー受領待ち
```

足りないのは、**停止理由を利用者向けの原因分類と一手へ写像する層**です。次の表が縮退運転の中心になります。

| 観測した停止理由 | 原因分類 | レベル | 利用者は直せるか | 示す一手 |
|---|---|---|---|---|
| 初期化が来ないままタイムアウト | 拡張機能が導入されていない、または無効 | `L2` | はい | 標準追加画面へ導く |
| 通信protocolの版が対応範囲外 | AlgoLoomと拡張機能が非互換 | `L2` | はい | **AlgoLoom本体の更新**を促す |
| 拡張機能のバージョンまたは権限が想定と違う | 想定外の配布物 | `L3` | いいえ | 停止して説明する |
| テンプレートの完全性を確認できない | AlgoLoom所有領域の破損 | `L2` | はい | 次回だけ初回設定へ戻す |
| 提出フォームの対象要素が見つからない | **AtCoder側の変更** | **`L1`** | **いいえ** | **縮退運転を提示する** |
| ブラウザを起動できない | 実行環境 | `L3` | はい | 停止して説明する |
| 折返し通信を確立できない | 実行環境 | `L3` | はい | 停止して説明する |

**「利用者は直せるか」の列が重要です。** すべてを「提出できないので手動で行ってください」にすると、AlgoLoomの更新で直る問題を放置させます。逆に、AtCoder側の変更を「利用者の環境の問題」として扱うと、利用者は直せない対処を試み続けます。

この写像は[認証状態とエラー分類](../architecture/atcoder-authentication.md#5-認証状態とエラー分類)を提出側へ拡張したものです。同じ原則（推測しない、安全側で停止する、次の一手を一つ示す）に従います。

### 3.5. 利用者への通知

伝える内容を4つに固定します。

| # | 伝えること | 理由 |
|---|---|---|
| 1 | **何ができないか** | 影響範囲を利用者が誤解しないため |
| 2 | **何は無事か** | [`F-SUBMIT-01` R4](../../spec/features.md#81-atcoder認証状態確認f-submit-01)は、認証エラーでローカルテスト、履歴閲覧、エクスポート、チェックポイントを止めないことを契約している。利用者が最も不安になるのは「これまでの記録は無事か」である |
| 3 | **今回どうするか** | 縮退運転で提出するか、中止するか |
| 4 | **恒久的にどうするか** | AlgoLoomの更新を待つか、更新するか |

[`F-SUBMIT-01` R5](../../spec/features.md#81-atcoder認証状態確認f-submit-01)の「行える行動を一つ示す」に従い、**推奨を一つ、代替を一つ**示します。選択肢を並べません。

表示例を示します。文言は実装時に確定します。

```text
提出の準備を自動化できません。

  理由    拡張機能がこのAlgoLoomと互換ではありません
          （拡張機能 0.3.0 / このAlgoLoomの対応範囲 0.1.x〜0.2.x）
  影響    提出だけです。ローカルテスト、履歴、これまでの記録は変わりません

  推奨    AlgoLoomを更新してください
            pipx upgrade algoloom

  今回だけ手動で提出する
            aloom submit --manual
          提出ページをブラウザで開きます。ソースコードの入力と
          提出操作はご自身で行ってください。
```

### 3.6. 縮退運転が採る経路

- AlgoLoomはソースコードと言語を準備し、[提出前確認](../../spec/features.md#82-提出前確認f-submit-02)の耐久保存を通常どおり行う
- 対象問題の公式提出ページをブラウザで開く
- 利用者が自分でソースコードを入力し、Turnstileと最後の提出操作を行う
- AlgoLoomは提出を自動化せず、判定を推測しない
- 履歴には、縮退運転による提出であることを区別して記録する

`L1`では認証ヘルパーがセッションを持つため、提出IDの取得と判定確認は`L0`と同じ経路で行えます。

### 3.7. 縮退運転は新しい状態を必要としない

`L2`では提出の有無をAlgoLoomが観測できません。これは[提出状態](../../spec/features.md#83-提出状態f-submit-03)の`REMOTE_STATUS_UNKNOWN`（送信の有無を断定できない事実）と同じ状況であり、既に「公式の提出一覧と利用者の確認」という回復経路が定義されています。

したがって**縮退運転のために新しい提出状態を追加しません。** `L1`は通常の状態遷移を使い、`L2`は`REMOTE_STATUS_UNKNOWN`と既存の回復経路を使います。

### 3.8. 採用しない選択肢

| 採用しない | 理由 |
|---|---|
| セッションを用いた直接HTTP提出への切り替え | [認証設計 §8](../architecture/atcoder-authentication.md#8-採用しない前提と方式)の不採用条件。Turnstileを回避することになる |
| 自動的な縮退運転への移行 | 外部作用を利用者の明示操作へ結び付ける契約に反する |
| 汎用的なDOM操作を拡張機能へ持たせる | §2.3の固定が崩れ、単一目的と最小権限の説明が成立しなくなる |
| 縮退運転を常時の基本経路にする | [`F-SUBMIT-01` R10](../../spec/features.md#81-atcoder認証状態確認f-submit-01)の一往復UXを常に手放すことになる |

利用者自身が公式サイトで手動提出する経路は、上記1行目の不採用条件に含まれません。禁止しているのは**セッションを使った自動送信**です。

### 4.2. TD-38へ渡す

引き渡し先は[`TD-38` 認証配布物とテンプレートのライフサイクル契約を確定する](../../TODO.md#td-38-認証配布物とテンプレートのライフサイクル契約を確定する)です。

- §2.3の固定項目を、拡張機能の契約として互換性表へ組み込む
- 固定する対象（拡張機能識別子、権限セット、配布元）と交渉する対象（通信protocol版）を分ける
- 後方互換の責任を拡張機能側へ置く。拡張機能は現行protocol版とその一つ前を話せるようにする
- 権限セットの変更を修正リリースではなく設計変更として扱う
- 事前検知に使うテンプレート検査の項目を確定する（§3.2）

### 4.3. TD-36へ渡す

引き渡し先は[`TD-36` AtCoder互換性確認の実装契約を確定する](../../TODO.md#td-36-atcoder互換性確認の実装契約を確定する)です。

- 提出フォームの要素指定をAlgoLoom本体側の知識として持つことを前提に、[`F-SUBMIT-05`](../../spec/features.md#85-atcoder側の変更検知と互換性確認f-submit-05)の変更検知と対応付ける
