# 拡張機能とヘルパーの配布：ステークホルダーと注意点

> 目的：方式Aが必要とする2つの配布物について、誰が何を決め、どの場面でどんな制約がかかるかを一枚に整理する。
>
> 位置付け：本書は2026年8月26日〜27日の調査と実測を整理したメモであり、配布方式を決める正本ではない。正本は[AtCoder認証設計 §3.6](../architecture/atcoder-authentication.md#36-配布物と実行ファイル署名の境界)、[配布方針ガイド §9.3](../operations/algoloom-distribution.md#93-atcoder認証用chrome拡張機能)、[Chrome拡張機能配布の運用リスクと緩和策](../project/chrome-extension-distribution-risks.md)とする。
>
> 作成日：2026年8月27日 ／ macOSとChromeの挙動、Chrome Web StoreとApple Developer Programの条件はいずれも変わり得るため、配布方式を変える前に公式資料と実測で再確認すること。

---

## ドキュメント概要

本書は、認証用Chrome拡張機能とAlgoLoom本体（認証ヘルパーを含む）という2つの配布物をめぐって、**登場人物ごとに何が起きるか**を整理します。同じ「配布」という語が、利用者、審査担当者、開発者で違う意味になることが混乱の原因だったため、場面ごとに分けて書きます。

## 0. 結論

- **Apple Developer Programが必要になるのは、審査担当者へヘルパーを一度渡す場面だけ**だった。利用者が何人になっても関係しない。普通のソフトウェアとは逆の構造である
- **拡張機能にAppleは一切関係しない。** HTML・CSS・JavaScriptであり、macOSの実行ファイルではない
- **`tar`はquarantine属性を展開先へ伝播する。** ブラウザ経由で取得されると実行ファイルは説明なく停止する。スクリプトは影響を受けない

## 用語

本書で紛らわしい2語を先に定義します。

| 語 | 何を表すか | 例 |
|---|---|---|
| **スクリプト** | **実装形式**。コンパイルせずそのまま実行できる書き方 | 審査担当者へ渡すファイルはPythonのスクリプトである |
| **フィクスチャ（fixture）** | **役割**。テストや検証のために用意する、内容または振る舞いが固定されたもの。**固定データ**と、本物の代わりに置く**代用部品**の両方を指す | 架空の問題データは前者。審査担当者へ渡す代用ヘルパーは後者 |

**別の軸の言葉なので、同じものが両方に当てはまります。** 審査担当者へ渡すファイルは、形式としてはスクリプトで、役割としてはフィクスチャです。「木製である」と「椅子である」が両立するのと同じです。

本書で「フィクスチャ」と書く場合は、断りがない限り**本物の認証ヘルパーの代わりに置く代用部品**を指します。**審査期間だけのもので、製品では使いません。**

## 1. 登場人物

### 1.1. 直接の当事者

| 登場人物 | 正体 | 拡張機能 | ヘルパー | AlgoLoomが制御できるか |
|---|---|---|---|---|
| **利用者** | AlgoLoomを使う人 | Chromeウェブストアから追加する | `pipx install algoloom`で本体ごと入る | ― |
| **審査担当者（reviewer）** | **Chromeウェブストアの審査を行うGoogle側の担当者** | **審査対象なので手元にある** | **持っていない。渡す必要がある** | 渡し方だけ |
| **公開者（owner / publisher）** | 拡張機能をCWSへ登録した主体。ここでは設計所有者 | 持っている | 持っている | ― |

**審査担当者がこの設計に登場する理由は一つです。** 拡張機能をChromeウェブストアで配るには審査を通す必要があり、審査担当者は実際に動かして判断します。ところが**拡張機能は単体では何も起きません**。

```
審査担当者が拡張機能をChromeに追加する
        ↓
        …… 何も起きない
```

content scriptが動くのは`http://127.0.0.1:<待受番号>/bootstrap`と`https://atcoder.jp/settings`の2か所だけで、前者を出すのはヘルパーだからです。ヘルパーがなければ同意画面すら表示されず、審査のしようがありません。動かせない拡張機能は機能しないものとして却下され得ます。

**したがって審査担当者へ「ヘルパー役」を渡す必要があります。** これが`TD-39`段階1で作った受渡し経路の目的です。

渡すのは本物のヘルパーそのものではなく、**同じように振る舞う代用部品（review fixture）**でも足ります。審査で確かめたいのは拡張機能だからです。

| | 本物の認証ヘルパー | review fixture |
|---|---|---|
| 実装形式 | Goのコンパイル済み実行ファイル | Pythonのスクリプト |
| 認証付き折返し通信のプロトコル | ― | **同じ** |
| `Host`・送信元・origin・トークン・本文上限・状態順序の検査 | ― | **同じ** |
| クッキーを1件受け取る | する | **する** |
| AtCoderへ本人照合しに行く | する | **しない** |
| OSの秘密情報保管庫へ保存する | する | **しない** |
| 使う場面 | 製品の認証。ずっと使う | 審査期間だけ。製品では使わない |

**拡張機能から見ると、両者は区別がつきません。** 同じプロトコルで同じ応答を返すためです。そのおかげで、拡張機能のソースを1行も変えずに審査へ出せます。

### 1.2. 条件を決める外部の主体

| 主体 | 何を決めるか | AlgoLoomが制御できるか |
|---|---|---|
| **Google（Chrome Web Store）** | 拡張機能の審査、署名、配布、**自動更新**、掲載の可否 | **できない** |
| **Apple（Gatekeeper・notarization）** | ダウンロードされたmacOS実行ファイルを実行できるか | **できない**（該当する経路を採らないことは選べる） |
| **PyPI** | AlgoLoom本体の配布 | 公開する版はAlgoLoomが決める |
| **AtCoder** | ログイン、提出フォーム、提出ID、判定の仕様 | **できない** |
| **Cloudflare（Turnstile）** | Bot対策の判定と対応ブラウザ | **できない** |

### 1.3. 時系列で見た登場順

```
【今】      公開者が拡張機能をCWSへ提出する
               ↓
【審査】    Googleの審査担当者が拡張機能を試す
               └─ ここでヘルパー役が必要      ← TD-39段階1で用意した経路
               ↓
【通過】    限定公開できる状態になる
               ↓
【V-12】    公開者が本物のヘルパーで検証を実行する
               ↓
【製品】    利用者が pipx install + ウェブストアから追加する
               └─ 本物のヘルパーを使う。審査担当者はもう登場しない
```

**審査担当者向けのフィクスチャは審査期間だけのものです。** 公開後は二度と登場しません。

## 2. 2つの配布物

### 2.1. 性質が異なる

| 観点 | 認証用Chrome拡張機能 | 認証ヘルパー |
|---|---|---|
| 実体 | HTML、CSS、JavaScriptのファイル群 | AlgoLoom本体の一部。`aloom`のサブコマンド |
| 配布経路 | Chrome Web Store（限定公開） | PyPI（`pip`、`pipx`、`uv tool`） |
| 取得する主体 | **Chromeが取得**し、Chrome所有のプロファイルへ展開する | 利用者がAlgoLoomを導入するときに一緒に入る |
| 版を決める主体 | **Chrome（自動更新）** | AlgoLoom |
| 可用性を決める主体 | **Google（審査・掲載）** | AlgoLoom |
| OSの実行ファイル保護の対象か | **対象外** | 対象になり得る |

### 2.2. 1つにまとめられない

| できないこと | 理由 |
|---|---|
| 拡張機能をAlgoLoomのパッケージへ同梱し、`pip`や`curl`で導入する | Chromeは一般利用者向けにChrome Web Store経由の追加しか受け付けない。`.crx`の直接インストールはmacOSとWindowsで無効で、手動読込にはデベロッパーモードが必要になる |
| 認証ヘルパーを拡張機能へ同梱する | 拡張機能はネイティブコードを実行できず、ブラウザーの起動、OSの秘密情報保管庫への保存、CLIへの応答を行えない |

### 2.3. 利用者から見た導入

```
1. AlgoLoomを導入する            pipx install algoloom          ← 1回
2. aloom auth login を実行する
3. AlgoLoomが専用ブラウザーで限定公開の掲載ページを開く
4. 利用者が標準追加画面で拡張機能の追加を承認する                   ← 手動はここだけ
5. AlgoLoomが固定の拡張機能識別子で導入完了を検出し、続きを自動で進める
```

利用者がウェブストアを自分で検索する必要はありません。

## 3. 誰が、いつ、どうヘルパーを入手するか

**本書で最も重要な表です。**

| 誰 | いつ | 入手方法 | quarantine属性 | Gatekeeper |
|---|---|---|---|---|
| **利用者** | 審査通過後、ずっと | `pipx install algoloom` | 付かない | **出番なし** |
| **審査担当者** | 審査中の一度だけ | **ファイルを直接ダウンロード** | 取得方法しだいで付く | **ここだけ問題になった** |

利用者はヘルパーを**ダウンロードしません**。ヘルパーは`aloom`の一部なので、単独で取得する場面が存在しないためです。

### 3.1. 普通のソフトウェアとは逆

| | 配布の形 | quarantineが付く相手 | 署名の要否 |
|---|---|---|---|
| 一般的なソフトウェア | 開発元がインストーラを配る | **全利用者** | 必要 |
| **AlgoLoom** | 利用者はパッケージマネージャで入れる | **利用者には付かない** | **不要** |
| AlgoLoomの例外 | 審査担当者へファイルで渡す | 取得方法しだい | ここだけ検討が要った |

**Apple Developer Programの問題は「審査中に数人へ一度渡す場面」だけのものでした。** 利用者が1人でも100万人でも変わりません。

### 3.2. この構造を保証しているのは設計の契約

[AtCoder認証設計 §3.6.5](../architecture/atcoder-authentication.md#365-契約)が次を定めています。

> **AlgoLoomは、OSの実行ファイル署名・notarization制度に依存する独立配布物を作りません。** 認証ヘルパーを、AlgoLoom本体とは別にダウンロードさせる実行ファイル、インストーラ、`.dmg`、`.pkg`、`.msi`として配布しません。

**この契約を破った瞬間に、利用者側でもGatekeeperが問題になります。** 利用者向けに`.dmg`や`.pkg`を配れば、ブラウザでダウンロードされてquarantineが付き、Developer ID署名とnotarizationが必要になります。契約はそのための予防です。WindowsのSmartScreen（Mark-of-the-Web）にも同じ効き方をします。

## 4. Apple Developer Programが必要になる条件

### 4.1. 判定表

Apple Developer Program（年額99 USD）が必要になるのは、Developer ID署名とnotarizationを行う場合、すなわち**quarantine属性が付く経路でmacOS向け実行ファイルを配布する場合**だけです。

| 端末への届き方 | quarantine属性 | Developer ID署名・notarization |
|---|---|---|
| 拡張機能をChrome Web Storeから追加する | 付かない。そもそも実行ファイルではない | 不要 |
| AlgoLoomを`pip`、`pipx`、`uv tool`で導入する | 付かない | 不要（**製品はこれ**） |
| 実行ファイルを`curl`、`git clone`、Homebrew等で取得する | 付かない | 不要 |
| 実行ファイルをブラウザー、メール、AirDrop等で受け取る | **付く** | **必要** |
| `.dmg`、`.pkg`、`.msi`等のインストーラを配る | **付く** | **必要** |

### 4.2. 2026年8月26日の実測（macOS 26.5、Apple silicon）

同一のad-hoc署名実行ファイルについて、quarantine属性の有無だけを変えました。

| 条件 | `spctl --assess --type execute` | 実行結果 |
|---|---|---|
| ad-hoc署名・quarantine属性なし | 拒否 | **成功** |
| ad-hoc署名・quarantine属性あり（`0001`、`0081`、`0083`） | 拒否 | **`SIGKILL`で停止** |
| quarantine属性付きのシェルスクリプト | ― | 成功 |
| quarantine属性付きの`.py`を`python3`で実行 | ― | 成功 |
| `curl`で取得し`tar`で展開した実行ファイル | 拒否 | **成功**。付く拡張属性は`com.apple.provenance`だけ |

この端末に導入済みの`uv`、`go`、`node`もすべてad-hoc署名で`spctl`に拒否されますが、通常どおり動作しています。**`spctl`の拒否は、パッケージマネージャー経由で導入したコマンドラインツール一般の通常状態です。**

実行を阻害するのはGatekeeperそのものではなく、**ダウンロード時にブラウザー等が付与するquarantine属性**です。

## 5. `tar`はquarantine属性を伝播する

### 5.1. 2026年8月27日の実測（macOS 26.5、Apple silicon）

同じ`.tar.gz`を、取得方法だけ変えて展開しました。

| 取得方法 | 展開後のquarantine属性 | ヘルパー（実行ファイル） | フィクスチャ（スクリプト） |
|---|---|---|---|
| `curl` + `tar` | 付かない | 実行できる | 実行できる |
| ブラウザー等でダウンロード + `tar` | **付く。`tar`が展開先へ伝播する** | **`SIGKILL`で停止** | **実行できる** |

### 5.2. この結果が変えた判断

当初は「`curl`で取得する経路（経路1）を主、スクリプトのフィクスチャ（経路2）を予備」と想定していました。実測により逆転しました。

- 経路1は**審査担当者の取得方法に依存**する。ブラウザーで取得されると説明のない`SIGKILL`になり、ダイアログも出ないため、担当者には壊れたツールに見える
- 経路2は**取得方法に依存しない**。1ファイル1コマンドで完結し、500文字のtest instructionsにも収まる

**2026年8月27日に、主経路をフィクスチャ（経路2）へ変更しました。** 経路1は製品相当ヘルパーを動かしたい担当者向けの任意経路として残します。

**「予備」として作ったものが、実際には唯一取得方法に依存しない経路でした。**

### 5.3. `curl`を使うことは回避ではない

回避とは、表示された警告を利用者に無効化または上書きさせることを指します。具体的には`xattr`によるquarantine属性の削除、右クリックからの実行、「このまま開く」の選択、`spctl`の無効化です。

`curl`やパッケージマネージャーでの取得は**警告を発生させません**。`uv`やHomebrewと同じ通常の導入手順です。この解釈は2026年8月26日に公開者が判断し、承認記録へ残しています。

## 6. よくある誤解と訂正

| 誤解 | 訂正 |
|---|---|
| 「MacでCWSへ拡張機能を配布するにはApple Developer Programが必要」 | **誤り。** CWSの要件はGoogle側の一回限り5 USDと審査だけで、Apple側の要件はない |
| 「Apple Developer Programが必要なのは、Mac App StoreでSafari拡張機能を配布する場合」 | **狭すぎる。** 正しくは、quarantine属性が付く経路でmacOSソフトウェア全般を配布する場合 |
| 「`spctl --assess`が拒否するなら配布できない」 | **誤り。** quarantine属性がなければ実行できる。`go`や`node`も同じ状態 |
| 「拡張機能にquarantineが付く」 | **誤り。** 拡張機能はmacOSの実行ファイルではなく、Chromeが自身のプロファイルへ展開する。Gatekeeperの対象外 |
| 「利用者が増えると署名が必要になる」 | **誤り。** 利用者はヘルパーをダウンロードしない。人数と無関係 |
| 「`curl`で取得させるのはGatekeeper回避」 | **誤り。** 警告を発生させておらず、無効化も上書きもさせていない |
| 「`V-12`が審査を通れば製品形態も通る」 | **誤り。** `V-12`が審査を受けるのはクッキーを1件読む拡張機能であり、製品形態は提出フォームの操作を加えるため単一目的の説明が変わる |

## 7. AlgoLoomが制御できないもの

配布物のうち、**拡張機能の版と可用性はAlgoLoomが制御できません。** 詳細は[Chrome拡張機能配布の運用リスクと緩和策](../project/chrome-extension-distribution-risks.md)を正とします。要点だけ再掲します。

| # | 事実 | 影響 |
|---|---|---|
| 1 | CWSで配布する拡張機能はChromeの更新機構で更新され、開発者は制御できない | 「新しい拡張機能 + 古いCLI」が定常的に発生する |
| 2 | バージョン固定は、visibilityが`Unlisted`または`Private`の場合は利用できない | 限定公開を選ぶ限り、この回避策は存在しない |
| 3 | ロールバックは旧版を新しい版番号で再公開する操作で、それも自動更新で全利用者へ配られる | 「戻す」ことはできない |
| 4 | 審査の所要時間は権限や変更内容により延び得る | 復旧時間を自分で決められない |
| 5 | Chrome 117以降、インストール済みの拡張機能がCWSから消えると利用者へ警告が表示される。malware判定なら自動無効化 | 取り下げが利用者に見える |

これらに対して、2026年8月26日に**緩和策H**（AtCoder依存部分を拡張機能から追い出す）と**緩和策D**（縮退運転）の採用を決めました。設計内容は[拡張機能の責任境界と提出の縮退運転設計](../features/extension-boundary-and-degraded-submission.md)を正とします。
